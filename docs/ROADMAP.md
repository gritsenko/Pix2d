# Pix2D — Long-Term Roadmap

> **Status:** Draft proposal · Last updated: 2026-09-04 · Baseline version: [v3.12.0](https://github.com/gritsenko/Pix2d/releases/tag/v3.12.0)
>
> This document is written for **both humans and AI coding agents**. Each work item includes context, acceptance criteria hints, and reference links so an agent can pick up a task with minimal extra briefing. Read [`CLAUDE.md`](../CLAUDE.md) and [`CONTRIBUTING.md`](../CONTRIBUTING.md) before starting any task. UI work must follow the project skill at [`.claude/skills/pix2d-ui`](../.claude/skills/pix2d-ui).

---

## 1. Vision & Positioning

**Pix2D is the asset pipeline tool for indie game developers: a modern, free, open-source sprite/pixel-art/animation editor that runs everywhere — Windows, Linux, macOS, Android, and the browser.**

Litmus test for every roadmap item:

> *Does this get an artist's asset into a running game faster?*

### Competitive landscape (for context, not imitation)

| Competitor | Strengths | Our differentiation |
|---|---|---|
| [Aseprite](https://www.aseprite.org/) ([source](https://github.com/aseprite/aseprite)) | Industry standard, huge feature set, scripting | Paid, desktop-only, dated UI. We win on: free/MIT, mobile + web, modern UI |
| [Pixelorama](https://orama-interactive.itch.io/pixelorama) ([source](https://github.com/Orama-Interactive/Pixelorama)) | Free, Godot-based, active community | We win on: native performance (SkiaSharp), mobile UX, stylus/pressure support |
| [Piskel](https://www.piskelapp.com/) | Zero-friction web editor | Effectively unmaintained. We win on: everything, once our web version is first-class |
| [LibreSprite](https://libresprite.github.io/) | Free Aseprite fork | Slow development. We win on: velocity, modern stack |

### Strategy in the AI era (2026)

Two real threats: (a) casual users generating assets instead of drawing them, (b) AI-native competitor editors. Two real advantages: (a) generative models are still bad at strict-palette, grid-consistent, animation-consistent pixel art — manual control remains technically necessary in this genre; (b) a solo maintainer with AI agents now matches the output of a small team, while competitors carry legacy codebases.

**Positioning answer:** Pix2D does not compete with generation — it *hosts* it. "AI drafts, human finishes, agent exports." And Pix2D itself becomes a tool that agents can drive (CLI + MCP), making it a node in AI game-dev pipelines rather than a victim of them. See [Track E](#track-e--ai--agent-integration).

## 2. How to read this roadmap (for agents)

- Work is organized into **Horizons** (time-ordered) and **Tracks** (thematic, continuous).
- Priority: `P0` = drop everything, `P1` = next release, `P2` = planned, `P3` = opportunistic.
- Before implementing: check [open issues](https://github.com/gritsenko/Pix2d/issues) for duplicates; link the roadmap item in the PR description.
- Definition of done for any item: code + tests (see [Track Q](#track-q--quality-infrastructure)) + entry in release notes draft + no regression in golden-image tests.
- Tech stack anchors: [Avalonia UI](https://docs.avaloniaui.net/) (currently 12.0.5), [Avalonia.Markup.Declarative](https://github.com/AvaloniaUI/Avalonia.Markup.Declarative), [SkiaSharp](https://github.com/mono/SkiaSharp) (currently 3.119.4), [SixLabors.ImageSharp](https://github.com/SixLabors/ImageSharp), .NET / C#. Web build runs on the Avalonia [WebAssembly backend](https://docs.avaloniaui.net/docs/guides/platforms/how-to-use-web-assembly).

## 3. Horizon 1 — Stabilization & Trust (0–3 months)

Goal: after the large v3.8.0 release, make export/selection/drawing bulletproof. Ship as a series of `3.8.x` patch releases.

### H1.1 Bug burn-down `P0`
- [x] Onion-skin layer leaks into export — [#230](https://github.com/gritsenko/Pix2d/issues/230). `Pix2dSprite.Layer.OnDraw` now gates the previous-frame ghost on `vp.Settings.RenderAdorners` (true only for the interactive editor viewport; false for every export/preview/thumbnail/clipboard/project-pack render), matching the existing `EditMode`/artboard-label/`BitmapNode` mip-cache convention. The "onion skin on by default / double-click to disable" note in the issue is stale (pre-3.8.0 animation-controls rework): defaults are now `false` and the toggle is single-click. **Follow-up (Track Q):** golden-image test comparing export with onion skin on/off — blocked on there being a test project.
- [x] Box-selection target movement interrupt — [#225](https://github.com/gritsenko/Pix2d/issues/225) (labeled Hot). Fixed by the transform-tool rewrite (`PixelTransformTool` / `SelectionController`): copy-on-write working-bitmap snapshots prevent tearing mid-transform (a638463), `MoveThumbNode` now raises a cancel event on interrupted drags (9dc8b41), and click-outside commits the transform instead of dropping it (4a5b18d) — a box-selection drag no longer disconnects partway through. **Follow-up (Track Q):** pointer-event regression test once a test project exists.
- [x] Pixel-perfect stroke flicker — [#241](https://github.com/gritsenko/Pix2d/issues/241). Resolved by the pixel-perfect drawing rework (swap-bitmap preview management `03b4282`, incremental preview + optimized bitmap handling `cf92167`, earlier `9e2e39f`); confirmed fixed in current builds.
- [x] Slider mouse-wheel support on desktop — [#242](https://github.com/gritsenko/Pix2d/issues/242) (small UX win, cheap). `SliderEx` adjusts on `PointerWheelChanged` while hovered (one notch = 1 step, Ctrl = 10, clamped to min/max); the event is marked handled so a parent `ScrollViewer` doesn't scroll instead.
- [x] **`SliderEx` redesigned to the Figma "filled value" control** ([`SliderEx.cs`](../Sources/Core/Pix2d.Core/UI/Shared/SliderEx.cs)). Replaced the old three-layout control (two-line / one-line / narrow-popup, each a stock `Slider` + `NumericUpDown`) with **one unified box** matching the redesign: a rounded track whose **accent orange→amber fill grows left→right as a background band** proportional to `(Value−Min)/(Max−Min)`, the uppercase label stacked over the current value inside the box, and the units on the right. Text stays in the light foreground tiers over the fill (the dark track is the *background*, never painted over the text — per design feedback). Interaction mirrors `Pix2dColorPicker`'s hue bar: **press + drag anywhere scrubs** (absolute mapping, pointer captured with `Handled` — carries over the #236 capture-steal hardening), the **mouse wheel** nudges (#242), and a **click without drag opens a keyboard text field** (autofocus + select-all, accent border) that commits on Enter / focus-loss and cancels on Esc or the ✕ button. Public API (`Label/Units/Minimum/Maximum/Value` + `ValueChanged`) unchanged, so all ~10 call sites keep working; the dead `LayoutMode`/`NarrowMode`/`NarrowWidthThreshold` props + enums were removed and the one consumer that set them ([`MagicWandToolSettingsView`](../Sources/Core/Pix2d.Core/Plugins/Drawing/UI/MagicWandToolSettingsView.cs)) now sets an explicit width. **Verified** end-to-end against a running Debug build via the AgentTools inspector (brush panel: fill band + light text on OPACITY, click→text-edit with ✕ on SIZE).
- [x] **Random crash while dragging the color slider** — [#253](https://github.com/gritsenko/Pix2d/issues/253). A **cross-thread use-after-free on the brush stroke-preview surface**, not a color-picker bug at all. Every color change reaches `DrawingLayerNode.DrawingColor` → `UpdateBrushPreview` → [`BasePixelBrush.GetPreviewSurface`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Brushes/BasePixelBrush.cs), which **cached the `SKSurface` on the brush and disposed the previous one on the next call** — while [`DrawingLayerNode`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Nodes/DrawingLayerNode.cs) still held that same surface in `_brushPreviewSurface` and drew it from **Avalonia's render thread** in `RenderBrushPreview` on every frame. Dragging a slider pushes one color change per pointer-move event, so the UI thread freed the native `SkSurface` hundreds of times a second while the render thread could be inside `SKCanvas.DrawSurface` on it — an access violation that kills the process outright, which is exactly why the reporter saw **no crash report** (`ICrashReportService` never gets a managed exception to forward). `ShowBrushPreview` stays `true` from the last canvas hover until the tool deactivates, so the preview keeps drawing while the color popup is open. Fixed by moving ownership: `GetPreviewSurface` now returns a **fresh, caller-owned** surface and caches/disposes nothing (its `_surface` field and the matching line in `Dispose()` are gone), and `DrawingLayerNode` guards `_brushPreviewSurface` with its own `Lock` covering the field read **plus** the `DrawSurface` calls, swapping under the lock and disposing the surface it drops — the same shape as the existing `_snapshotLock`, and the two are never nested. That keeps the leak fix the dispose was originally added for (`f21dbbb`, 2026-06-18) without the race. **Covered by ScenarioTests** (new *Brush preview surface ownership* scenario, 283/283 green) pinning the ownership contract the race depends on — a brush must not free a surface it has handed out, `Dispose()` included, and the layer must free the one it replaces; **confirmed discriminating**: 2 of the 3 checks fail against the pre-fix code. *The race itself is timing-dependent and not reproducible headlessly — worth a manual pass dragging the hue slider with a brush tool active in a real build.*
- [x] Palette slider interruption — [#236](https://github.com/gritsenko/Pix2d/issues/236). Not reproducible on desktop; hardened preventively: `Pix2dColorPicker` now marks its color-square / hue-slider pointer events `Handled` so a parent `ScrollViewer`'s touch `ScrollGestureRecognizer` can't hijack the pointer mid-drag and steal the capture (the capture-steal is what interrupted the drag on touch). Same class of fix as the slider mouse-wheel handling in [#242].
- [x] Grid toggle did nothing — enabling "Show grid" in the grid-settings flyout never showed the grid. `GridSettingsView.State` captured a single `ViewPortState` instance at construction; the flyout is built once with `MainView` (before the first real project is current, and stale after every tab switch), so toggles wrote to an orphaned `ViewPortState` that no watcher — `SnappingService`/`ViewPortRefreshService` both rebind via `WatchForCurrentProjectViewPort` — ever observed. Fixed by making the view resolve `AppState.CurrentProject.ViewPortState` **live** on every read/write and rebind through `WatchForCurrentProjectViewPort` (which also reflects the Ctrl+. `ToggleGrid` shortcut back into the switch) — the same stale-binding gotcha documented in `CLAUDE.md`. Verified end-to-end against a running Debug build via the AgentTools inspector (flyout switch toggle now drives the active project's grid node in both directions).
- [x] Narrow-screen (phone-portrait) dialogs/banners overflowed the viewport. On a ~290px window the telemetry-consent dialog (fixed `.Width(400)`), the unsaved-changes dialog (three fixed 100px buttons), and the crash-recovery banner (non-wrapping horizontal row) spilled off-screen. Fixed at two levels: (1) systemic — [`PopupView`](../Sources/Core/Pix2d.Core/UI/Shared/PopupView.cs) (the dialog host) now clamps its width to the viewport (`MaxWidth` + a restore-able `MinWidth` clamp) and re-fits on parent resize/rotation via a `Bounds` subscription bound in `ApplyPositionForCurrentLayout`; [`DialogContainer`](../Sources/Core/Pix2d.Core/UI/Shared/DialogContainer.cs) now starts `IsOpen(false)` so the *first* dialog shown (startup telemetry prompt) actually fires `OnOpened` and gets the clamp. (2) per-view — telemetry/unsaved dialogs use `MaxWidth` + stretched-column button rows (no fixed widths), text wraps; the recovery banner ([`MainView`](../Sources/Core/Pix2d.Core/UI/MainView.cs)) stretches with margins under a `MaxWidth(560)` cap with a wrapping text column. Also localized + wrapped the previously hardcoded unsaved-changes strings. Verified end-to-end via the AgentTools inspector (`set_window_size` 290→266px clamp, `layout_audit` clean, no overflow) for all three at phone-portrait width.
  - **Follow-up (done):** repositioned the crash-recovery banner from centre-screen to a top notification zone directly under the top toolbar (a Row-2 slot in the full-width top strip in [`MainView`](../Sources/Core/Pix2d.Core/UI/MainView.cs)); on a narrow screen its Dismiss button now wraps onto its own line. Re-enabled the previously commented-out **rate/review prompt** in the same zone and made it responsive — [`RatePromptView`](../Sources/Core/Pix2d.Core/UI/RatePromptView.cs) now uses the shared `notify-card`/`notify-content` styles (centred one-row on desktop, stretched + actions-stacked on narrow) and its `IReviewService` ctor arg defaults to null so it builds on desktop/web (where the prompt stays hidden) instead of throwing. Both banners share global `notify-card`/`notify-content` styles in [`AppStyles`](../Sources/Core/Pix2d.Core/UI/Styles/AppStyles.cs) (global so they also reach the nested `RatePromptView`). **Tool/action bars** ([`TopToolUiContainer`](../Sources/Core/Pix2d.Core/UI/TopToolUiContainer.cs), [`ActionsBarView`](../Sources/Core/Pix2d.Core/UI/ActionsBarView.cs)) — especially the wide selection-tool settings — now scroll horizontally instead of clipping off-screen: each is a horizontal `ScrollViewer` whose width is clamped to the window client size via [`ViewportSizeExtensions.ClampMaxWidthToViewport`](../Sources/Core/Pix2d.Core/UI/Shared/ViewportSizeExtensions.cs) (a plain `MaxWidth` or star column can't bound them here — the bottom side-panels contaminate the grid's Auto columns' width). Verified via AgentTools at 290/800/900px.
- [x] Ctrl+S on a PNG-backed project should overwrite the source image — [#200](https://github.com/gritsenko/Pix2d/issues/200) (Hot, `complexity:low`). When a project was opened from a flat `.png` and is still a single sprite / single layer / single frame, `ProjectService.SaveCurrentProjectAsync` now writes back to the original PNG (via the existing `IExportService.ExportNodesToFileAsync` render path) instead of popping a "Save as .pix2d" dialog. `ProjectState.File` already keeps the opened source reference, so no new tracking was needed; the extension match is case-insensitive. Adding a layer/frame/artboard changes the shape so it correctly falls through to the project save. Desktop-only (Android/WASM use `UseInternalFolder`). One-file change in [`ProjectService.cs`](../Sources/Core/Pix2d.Core/Services/Project/ProjectService.cs) (+ `IExportService` ctor dep). **Verified** (manual, desktop): editing a PNG-backed single-layer/frame project and pressing Ctrl+S overwrites the source image silently; adding a layer/frame falls back to the `.pix2d` Save As.
- [x] Palette doesn't highlight the picked color — [#220](https://github.com/gritsenko/Pix2d/issues/220) (Hot, `bug`, `complexity:low`). Root cause: the [`ColorPalette`](../Sources/Core/Pix2d.Core/UI/Shared/ColorPalette.cs) control had no concept of a "selected" swatch — every swatch drew the same fixed border, and nothing compared the current color to palette entries. Added a `SelectedColor` `DirectProperty` (the Markup.Declarative generator auto-emits the `.SelectedColor(...)` binding) that highlights the matching swatch (2px full-opacity white border) via an in-place restyle (no rebuild churn during HSV drag), and bound it to the existing `state.SelectedColor` — which already tracks the eyedropper pick through `SpriteEditorState.CurrentColor` — on both the Recent and Custom palettes in [`ColorPickerView.cs`](../Sources/Core/Pix2d.Core/UI/ColorPickerView.cs). **Verified end-to-end** via the AgentTools inspector: selecting a color highlighted the matching swatch in both palettes (2px white ring) while non-matching swatches kept the dim border.
- [x] Show the eyedropper cursor + toolbar highlight while Alt is held over a brush — [#184](https://github.com/gritsenko/Pix2d/issues/184) (`UX/UI`). Holding Alt over a brush-family tool (`PixelBrushToolBase`: Brush/Eraser/pixel Shape) makes it pick a color instead of draw, but there was no visible feedback until now. Added a transient `ToolsState.IsColorPickerModeActive` flag that [`SkiaCanvas`](../Sources/Core/Pix2d.Core/SkiaCanvas.cs) (owns key events + cursor) sets on Alt-down/clears on Alt-up (and on tool switch, so it can't stick), driving a picker cursor (`StandardCursorType.Cross`), and had [`ToolItemView`](../Sources/Core/Pix2d.Core/UI/ToolBar/ToolItemView.cs) OR the eyedropper's toolbar highlight on the same flag. Three small files, no new subsystem. *Note: Avalonia has no stock eyedropper cursor — `Cross` is the zero-asset approximation; a custom bitmap cursor from icon glyph `\xE91B` is a possible follow-up.* **Verified** (manual, desktop).
- [x] `ArgumentOutOfRangeException` in `LayersView.State.InvalidateThumbnailItems` — Sentry crash on 3.9.0 (Android, 19 events / 6 users). Root cause: the index-based overload did `Layers[ReverseIndex(index)]` where `ReverseIndex = Layers.Count - index - 1`. An operation's `AffectedLayerIndexes` are captured at operation time and can fall outside the UI's `Layers` mirror (operation targeting a different sprite/frame than the one displayed, a layer-count mismatch, or the mirror not yet reloaded on tab/artboard switch), producing a negative or too-large index that threw on the indexer — surfacing as an unobserved-task crash via `OnOperationInvoked`. Fixed by bounds-checking the reversed index in [`LayersView.cs`](../Sources/Core/Pix2d.Core/UI/Layers/LayersView.cs) and skipping out-of-range entries (matching the null-safe `FirstOrDefault` pattern of the sibling `Layer`-based overload); a skipped thumbnail refreshes on the next `ReloadLayers`, so it's cosmetically harmless.
- [x] `NotImplementedException` — Sentry crash on 3.9.0 (Android, "Arg_NotImplementedException", no frames). The most probable trigger: **Bake effect** (layer effects UI → `EffectsService.BakeEffect` → `BakeEffectOperation`) called [`EffectExtensions.ApplyToBitmap`](../Sources/Core/SkiaNodes/Extensions/EffectExtensions.cs), which unconditionally threw `NotImplementedException` — baking *any* layer effect crashed on every platform. Implemented it mirroring `SKNodeRenderer.RenderEffectsToSurface` (bitmap → surface, `effect.Render(rc, surface)`, pixels read back); verified for all three effect types (Replace/Back/Overlay: grayscale converts, shadow preserves content + offsets, outline renders). Also defused the other reachable NIE stubs: `AndroidPlatformStuffService.ToggleTopmostWindow`/`OpenAppDataFolder` and the browser `OpenAppDataFolder` are safe no-ops, and the `ClipboardCommands` General-context Copy/Paste/Cut placeholders log a trace instead of throwing. *(Correction, 2026-07-28: those placeholders are **not** actually bound to Ctrl+C/V/X — `ClipboardCommands` is registered nowhere, so they are unreachable dead code rather than live commands. Discovered while wiring the General action bar; see the General-context entry below.)* Remaining NIE stubs (`BitmapNode.Clear`/`ModifyBitmap`/…, `SelectionService.SelectNext`, `EditContext.Title`) are verified-unreachable dead code. See the Track Q diagnostics entry for why the Sentry event was frame-less and how that's fixed.
- [x] `InvalidOperationException: "Bitmap is null"` on **Undo** — appstat handled-error on 3.9.0 (Android, 11 events / 1 user, burst). Stack: `BitmapNode.GetData` → `Pix2dSprite.GetData` → `DrawingOperationWithDiffState.ApplyChanges` → `OnPerformUndo` → `OperationService.Undo`. The undo diff-apply reads `target.GetData()`; a frame's `SpriteNode` can reach that path with a null `Bitmap` (partial session restore, or the node's pixels disposed on unload while the operation history still references it). The hard throw aborted the undo *and* left the stack inconsistent (`Undo` pops the op but never pushes it to redo — line ~239/244 in [`OperationService.cs`](../Sources/Core/Pix2d.Core/Services/OperationService.cs)), so hammering undo spammed the error. Fixed in [`BitmapNode.cs`](../Sources/Core/Pix2d.Shared/CommonNodes/BitmapNode.cs): `GetData`/`SetData` now go through an `EnsureBitmap()` helper that lazily re-allocates a blank bitmap sized to the node's known `Size` (mirroring the existing lazy create in `OnSizeChanged`, `Pix2DAppSettings.ColorType`), so the diff re-applies and undo keeps working; it still throws only when `Size` is genuinely unknown (0×0 — nothing recoverable). The frame-less `NullReferenceException` on 3.9.0 (4 events / 2 users) whose first occurrence falls inside the *same* burst window is most likely a downstream cascade of this broken-undo state and should subside with this fix.
- [x] `ArgumentOutOfRangeException` in `TimeLineView.State.OnOperationInvoked` — appstat handled-error on 3.9.0 (Android, 8 events / 3 users). Exact sibling of the `LayersView` thumbnail crash above: on undo/redo of an `ISpriteEditorOperation`, `Frames[index]` used the op's `AffectedFrameIndexes` (captured at operation time) directly, which can exceed the active sprite's current `Frames.Count` (frames deleted, or a different artboard now drives the timeline). Fixed by bounds-checking the index and skipping out-of-range entries in [`TimeLineView.cs`](../Sources/Core/Pix2d.Core/UI/Animation/TimeLineView.cs) — a skipped frame thumbnail refreshes on the next `ReloadFrames`.
- [x] `IndexOutOfRangeException` in `DrawingOperationWithDiffState.ApplyChanges` on **Undo** — appstat handled-error on 3.9.0 (Android/Windows, 22 events / 2 users). Stack: `ApplyChanges` → `OnPerformUndo` → `OperationService.Undo` → `EditCommands.Undo`. Sibling of the "Bitmap is null on Undo" fix above (same method) but a *size-mismatch* failure mode: the undo replays a run-length diff whose block lengths sum to the target's pixel count captured when the operation ran, writing them sequentially into `target.GetData()`. If the drawing target was resized since (crop/resize replayed out of order, or a different-sized artboard is now the target), the runs overrun the current buffer → out-of-range write. Fixed in [`DrawingOperationWithDiffState.cs`](../Sources/Core/Pix2d.Shared/Operations/Drawing/DrawingOperationWithDiffState.cs): `ApplyChanges` now compares the total diff length against the current pixel buffer and skips the apply (logged via `Logger.Trace`) when they differ — avoiding both the crash and the memory corruption a partial write would cause on a mismatched buffer.
- [x] Autosave temp-file races — appstat handled-errors on 3.9.0/3.10.0 (Android, 5 signatures: `FileNotFoundException`/"Could not find file"/"used by another process" on `Sessions/active/<id>/frames/<key>.png.tmp`). Root cause: `AutoSaveService.ForceSaveSync` (Android `OnPause` / window close) runs the commit on a background task with a bounded wait; on **timeout it releases `_commitLock` while that commit keeps running**, so a later periodic `TickOnceAsync` can start a *second* `CommitAsync` on the same store, colliding on the deterministic `<key>.png.tmp` path — the create fails ("used by another process", `FileShare.None`), or the sibling's `File.Move` already consumed the temp → FileNotFound. Fixed by adding a per-store commit gate (`SemaphoreSlim`) in [`IncrementalSessionStore.CommitAsync`](../Sources/Core/Pix2d.Core/Services/AutoSave/IncrementalSessionStore.cs) so an overlapping commit waits instead of racing, restoring the one-commit-per-store invariant at the store level (where it matters) rather than only at the service lock.
- [ ] `InvalidOperationException: "Peer instance does not implement T."` — appstat handled-error on 3.9.0 (Android, 4 events / 2 users, single burst incl. an emulator). Frame-less; thrown inside Avalonia's automation-peer subsystem (triggered by Android accessibility/TalkBack enumerating peers), not app code — no custom `AutomationPeer` exists in the repo. Not app-fixable at the current stack detail; revisit if it recurs with a usable frame or on an Avalonia upgrade.
- [ ] **3.10.0 store rollout — three frame-less appstat signatures (desktop/Windows, `SentryLevel.Fatal`).** First seen on the 3.10.0 build that shipped consent-gated telemetry, so they were **surfaced, not introduced**, by the new `CaptureHandled`/`CaptureFatal` path — each carried only its exception header (type + message), no frames. Signatures: (1) `ArgumentException: "UnsupportedType (Parameter 'Decimal')"` (6 events / 1 user, 2-min burst) — string isn't anywhere in the source, so it's a library resource thrown in a real path (serialization/conversion of a `Decimal`); ruled out the new analytics client (`AppStatTrackingClient.WriteValue` handles `decimal`, and analytics metrics are `double`). (2) `Exception: "Unable to allocate pixels for the bitmap."` — SkiaSharp OOM allocating an `SKBitmap` (large canvas resize/export/import). (3) `UnauthorizedAccessException: "Access to the path 'C:\Windows\System32\…png' is denied."` — **root-caused and fixed, see the next item**. (1) and (2) remain **blocked on a usable stack**; the Track Q *reported-exception stack guarantee* below makes the next occurrence locatable. Likely follow-ups once framed: treat expected IO (`UnauthorizedAccessException`/`IOException`) on export/save and `SKBitmap` allocation OOM as **handled, user-facing** errors (toast/dialog) instead of fatals that reach the global handlers.
- [x] **Save/export dialogs defaulted to `C:\Windows\System32`** — `UnauthorizedAccessException` recurring across 3.10.0 → 3.11.1 (Windows, 4 signatures, one per user-typed file name: `bd.png`, `bobbin.gif`, `Shiney.png`, `Coucher de soleil.png`). Root cause: `AvaloniaFileService` never set `SuggestedStartLocation` on any picker, so the Win32 dialog opened on the **process working directory** — which is `C:\Windows\System32` when Pix2d is launched through its file association (`shell\open\command` passes no working directory). Users accepted that folder and the write failed. The `contextKey` parameter threaded through every `IFileService` overload for exactly this purpose was accepted and **silently ignored**, and its reserved settings key `SettingsConstants.FileServiceContexts` was unused. Fixed in [`AvaloniaFileService`](../Sources/Core/Pix2d.Core/Services/AvaloniaFileService.cs): open/save/folder pickers now start in the last folder used for that context (persisted as a `contextKey → path` map under `FileServiceContexts`), falling back to **Documents** — so the default is always writable and the documented per-context folder memory finally works. Two latent bugs in the same area fixed alongside: [`AvaloniaFolder.GetFileName`](../Sources/Core/Pix2d.Core/Common/FileSystem/AvaloniaFolder.cs) called `Path.Combine` with a *single* argument, dropping the folder and handing a bare relative name to `File.OpenWrite` (another CWD write, plus a de-dup `File.Exists` check that probed the wrong directory and so silently overwrote existing exports); and `AvaloniaFolder.Path` used `Uri.AbsolutePath`, which yields `/C:/a/My%20Art` — not a usable filesystem path. Split into `GetFilePath` (full path, for raw `File`/`Directory` APIs) and `GetUniqueFileName` (name only, for `IStorageFolder.CreateFileAsync`). Shipped in **v3.11.2**; all four `System32` signatures resolved in appstat on 2026-07-27. The sibling signature on a user's *own* file (`…\Documents\Spider_SpriteSheet.png`) is **not** covered by this and stays open — that write was genuinely denied (read-only / locked / sync-held file), which is the "treat expected IO as a handled, user-facing error" follow-up noted above, not a bad default folder.
- [x] **3.11.1 crash hardening.** Two independent fixes shipped together: (1) [`ExportView`](../Sources/Core/Pix2d.Core/UI/Export/ExportView.cs) now catches exceptions from `RenderToBitmap` when generating an export preview, so an oversized preview render (OOM on a very large canvas) shows a graceful state instead of crashing the app. (2) [`MainActivity.DispatchKeyEvent`](../Sources/Heads/Pix2d.Droid/MainActivity.cs) (Android) now swallows an `IndexOutOfRangeException` coming from an Avalonia.Android bug in its own key-dispatch internals — not app code, but it was reaching the app as an unhandled crash.
- [x] **Timeline frame-reorder / delete `ArgumentOutOfRangeException`** — two new appstat signatures on 3.11.1 (Android): `"Index must be within the bounds of the List"` (fatal, on `List<LayerFrameMeta>.Insert` in [`ReorderAnimationFramesOperation`](../Sources/Core/Pix2d.Core/Plugins/Sprite/Operations/Animation/ReorderAnimationFramesOperation.cs)) and `"Index was out of range"` (on `Layer.GetFrameByIndex` in [`DeleteAnimationFrameOperation`](../Sources/Core/Pix2d.Core/Plugins/Sprite/Operations/Animation/DeleteAnimationFrameOperation.cs)). Root cause: the timeline `Frames` collection carries an extra `IsAddFrame` placeholder at index == frameCount, and [`ItemsListContextDragBehavior`](../Sources/Core/Pix2d.Core/Common/Behaviors/ItemsListContextDragBehavior.cs) treated it as an ordinary draggable item — dragging it, or dropping a real frame onto its slot, produced a `newIndex`/`oldIndex` one past the real-frame range. Gated to platforms that can report a process exit — desktop never reads it back and several instances can run at once, which would make a single shared file meaningless. Staleness is bounded (24 h) and reported as `ContextAgeMs`, so misleading idle context degrades to *no* context.

SIGABRT keys on its abort message; ANRs get their own path (a thread dump is not a tombstone). Pix2d opens: …*) instead of leaking `First()`'s "Sequence contains no matching element" into a dialog, and `ProjectService.OpenFilesAsync` now builds the new scene **before** `CloseCurrentProject()`, so a failed open no longer half-closes the user's project (file reference cleared, `ProjectCloseMessage` already sent) and leaves them with nothing. So the intent is already typed APK before it leaves the trampoline and no filter of ours can see it — claiming that mime is exactly the bug this whole item fixed. Also fixed on the way: `SpritePngSequenceExporter.Export` was `async void` and called un-awaited, so a failed sequence export reported success and swallowed the error — it's now an awaited `Task` that renders frames lazily (a long animation at high scale no longer holds every frame bitmap at once); `AvaloniaFolder.GetSubfolder`/`GetSubfolderAsync` were `NotImplementedException` stubs (the async form now goes through the storage provider, so it also works where the picked folder has no filesystem path — Android SAF, browser); `SvgImageExporter` became an `IStreamExporter` (it already had the stream, just not on the interface — now shareable and batch-writable through the generic path); and `PngImageExporter` moved off the `"project"` folder-memory context onto `"export"` like every other exporter, so a PNG export no longer reopens the folder the `.pix2d` was last saved to. en + ru localized. **Batch preview is a master/detail pair** modelled on [`MainMenuView`](../Sources/Core/Pix2d.Core/UI/MainMenu/MainMenuView.cs): for >1 artboard the preview pane grows an artboard list ([`ExportListItem`](../Sources/Core/Pix2d.Core/UI/Export/ExportListItem.cs) rows: thumbnail + the base name the output will be written under + `w × h px · n files · ~size`). **Wide** keeps preview left / list right (240 px) with both always visible; **Narrow** makes the list the landing view and covers it with the preview plus a **← Back** button once an artboard is picked (the list is declared first in the grid so the opaque preview covers it in the shared cell). Column placement lives in `Style<T>` blocks keyed on `VisualStates.Narrow()`, but **visibility is computed in the view-model** — a style setter loses to a binding, so mixing the two silently breaks; `UpdateMasterDetailVisibility()` reads the watched `UiState.VisualState` so a resize re-evaluates it. Row metrics are the *real* exporter output, so `MeasureItemsAsync` walks the rows one at a time yielding to the dispatcher (`DispatcherPriority.Background`) between them — rows fill in progressively, a 23-artboard scene stays responsive, and the Output line carries `n/N …` until the last lands; a new schedule (scale / exporter option / scope) cancels the run in flight, as does closing the dialog. Thumbnails are scale-independent and rendered at most 64 px, so a scale change re-measures without re-rendering them. The old 12-artboard size-estimate cap is gone: the same measurement path now serves both the list and the single-artboard Output string, so there is exactly one place that turns an artboard into a size. **Next:** a per-artboard export toggle (`NodeExportSettings.ExportMode` already exists on `NodeDesignerState` and is unused) so a scene can mark scratch artboards as never-export, progress/cancel in the `UiBlocker` for large batches, and scrolling the selected row into view when the dialog opens.

The library is a `List<PaletteData>` persisted via a new `AppSettings.SavedPalettes` property (the reflection-based [`SettingsService`](../Sources/Core/Pix2d.Core/Services/SettingsService.cs) only round-trips keys that exist as `AppSettings` properties — arbitrary keys silently no-op). `IPaletteService`/[`PaletteService`](../Sources/Core/Pix2d.Core/Services/PaletteService.cs) gained `SetPaletteColors` + `Save/Load/DeleteSavedPalette` + the three `*Async` IO methods (now `// Depends on: ISettingsService, IFileService`). Saved lists are **submenus** (arbitrary length never overflows) and the flyout opens downward from a top-anchored button (no bottom clip — the earlier `ComboBox`/bottom-bar layout clipped its dropdown). Localized (en + ru). **Remaining:** a format dropdown in the save dialog (the shared `GetFileToSaveWithDialogAsync` groups all extensions into one filter, so non-`.gpl` export needs a typed extension) and `.ase` palette import (folded into the `.ase` importer work below).
- [x] **`.piskel` import** — free user migration from Piskel. Import-only ([`PiskelFormatPlugin`](../Sources/Core/Pix2d.Core/Plugins/ImageFormats/PiskelFormat/PiskelFormatPlugin.cs), loaded by the base bootstrapper so every head gets it — it is pure managed JSON + Skia); writing the format back would only help move art *out* of Pix2d. "JSON-based, trivial" undersold it: the format has two traps, both documented in [`PiskelDocument`](../Sources/Core/Pix2d.Core/Plugins/ImageFormats/PiskelFormat/PiskelDocument.cs) — (1) `piskel.layers` holds JSON **strings**, each a separately serialized layer that must be parsed a second time; (2) a chunk's `base64PNG` is a horizontal sheet and its `layout` maps **cell → the frame indices that cell fills**, which is how Piskel deduplicates repeated frames, so reading cell *i* as frame *i* silently scrambles the animation of any sprite with a repeated frame. A frame no layout covers imports as transparent rather than being dropped (that is how Piskel stores a blank frame, and dropping it would leave the timeline ragged), and frames sharing a cell get independent bitmap copies since they become separately editable. `modelVersion` other than 2 is refused with a message instead of guessed at. **Flow:** new `ImportFileKind.LayeredDocument` / `ImportMode.LayeredDocument` — one file is one whole sprite wherever it was dropped, so nothing is asked; it shares its execution with the GIF path, generalized to `ImportWholeDocumentsAsync`, which passes the decoded `ImportData` through untouched. That is what preserves layer **names and opacity**, for which `LayerPropertiesInfo` gained `Name` and `SpriteImportApplier` now applies both (a no-op for flat PNG/GIF imports, which leave the defaults). **Covered by ScenarioTests** (10 checks, 237/237 at the time) including the real registration + flow end-to-end, and **confirmed discriminating**: reading cells positionally instead of through the layout fails the three pixel-mapping checks.

### H2.4 Animation to competitive parity `P2`
- [x] **Add-frame tile at the end of the timeline** (3.11.1) — [`TimeLineView`](../Sources/Core/Pix2d.Core/UI/Animation/TimeLineView.cs) now appends a dedicated `+`-style tile after the last frame (bound to the new `ISpriteAnimationCommands.AddFrameAtEnd` → `SpriteEditor.AddFrameAtEnd`, which pushes an `AddAnimationFrameOperation` with `previousIndex = -1`), a quicker path than duplicating/inserting after the current frame when appending to the end of an animation.
- [x] Animation **tags/ranges** within one document (idle / run / jump), exported as ranges in metadata. Shipped with H2.2 PR-3 (see that entry): `Pix2dSprite.AnimationTags`, authored in the new animation-properties popup, surfaced on the timeline tiles as a coloured underline, emitted as `meta.frameTags` and selectable with `pix2d export --tag`. **Remaining:** an in-timeline tag lane with drag handles (deliberately deferred — a scroll-synced overlay on the virtualized tile list is its own project), and per-tag export from the in-app Export dialog.
- [x] Per-frame duration (ms), not just global FPS. Shipped with H2.2 PR-3: a sparse `Pix2dSprite.FrameDurations` override list over the shared timeline (`0`/absent = "use `1000/FrameRate`"), authored per selected frame, marked on the tile with a corner dot, honoured by in-app playback (the timer became a chain of one-shots re-armed per frame, so the preview can't disagree with the exported metadata) and emitted as each frame's `duration`. **Remaining:** the Export dialog's own preview timer has the same fixed-interval flaw and still plays at a uniform rate.
- [x] **Linked cels (share one image across frames)** — memory + workflow win for static parts. **The substrate already existed and was invisible:** `LayerFrameMeta.NodeId` has always let several frames point at one `SpriteNode`, and `DuplicateFrame` has always handed the copy the source's node — sharing was a pure memory optimisation that `EnsureFrameHasUniqueSprite` (copy-on-write) silently broke on the first edit. The feature is making that sharing **deliberate**, and it turns on one early return: a frame marked linked is not split by an edit, so the write reaches the shared node and every linked frame changes together. **Why it needs a flag rather than "shared == linked":** existing projects already contain incidentally shared nodes from a duplicate-without-edit, and reinterpreting those as links would make editing one frame of an old file silently change another — so `LayerFrameMeta.IsLinked` (`"ln"`) is absent in old files, deserialises to `false`, and they keep copy-on-write. Invariant held by [`Pix2dSprite.Layer`](../Sources/Core/Pix2d.Shared/CommonNodes/Pix2dSprite.Layer.cs): the frames on one node are all linked or all unlinked — which is why `DuplicateFrame` of a *linked* frame now takes its own copy eagerly instead of becoming a silent third member. API: `LinkFrames`/`UnlinkFrame`/`IsFrameLinked`/`GetLinkedFrameIndices`; unlinking the second-to-last member drops the link entirely rather than leaving a one-member "link" that still blocks copy-on-write. **Per layer, not per sprite** — that is what a cel is, and it is the use case: a static background sharing one image while the layers above keep animating. Undo is one [`LinkAnimationFramesOperation`](../Sources/Core/Pix2d.Core/Plugins/Sprite/Operations/Animation/LinkAnimationFramesOperation.cs) restoring a **snapshot** of the layer's frame table + node set, because linking discards the followers' bitmaps and a discarded bitmap cannot be recomputed (the same reasoning as the animation-metadata snapshot). Commands `Sprite.Animation.LinkAllFrames` / `UnlinkFrame`, both no-ops when they'd change nothing so neither pushes an empty undo step; the timeline marks a linked cel with a chain glyph, re-read on layer switch since the marker follows the *selected* layer. en + ru localized. **Covered by ScenarioTests** (13 checks, 251/251 total, sweep 80 executed / 0 findings) — the two that carry the feature are "an edit propagates across a link" and "a plain duplicate still copy-on-writes", plus undo restoring each frame's own pixels and a save/load round-trip where both frames must resolve to the *same* node. **Confirmed discriminating**, and one check had to be strengthened to earn that: the duplicate-of-a-linked-frame test originally drew on the duplicate, which copy-on-write splits anyway — it now draws on the linked *original* and asserts the duplicate does not follow. **Track Q fallout:** `LayerFrameMeta` was missing from the serialization contract guard, so adding `ln` to the format's own frame table drew no warning at all; it is now pinned as `~LayerFrameMeta` (22 types). **Verified on a running Debug build** through the AgentTools inspector — linking three frames marks all three tiles, drawing on one of them lands on all three (`pix2d_pixels` per frame), and unlinking the middle frame drops its marker while the other two keep theirs. That pass found the two defects the headless tests structurally could not: (1) the marker was first drawn as a chain **glyph**, but `pix2d-icons-v3` is a curated icon font with no link glyph, so the borrowed codepoint rendered as nothing — it is now a band along the tile's top edge, mirroring the tag band on the opposite edge and needing no font at all; (2) `TimeLineView.OnOperationInvoked` rebuilds its tiles only for an explicit **allow-list** of operation types, and `LinkAnimationFramesOperation` was not on it, so the link fell through to the branch that only invalidates thumbnails — the pixels updated while the markers stayed stale. Both are the class of bug a headless harness cannot see, which is the argument for this pass existing. *(Unrelated find, filed separately: the tools panel hit-tests outside its clipped ScrollViewer, so invisible tool buttons sit over the timeline's leftmost tiles.)*
- [ ] Export animated **GIF** — quality fixed: the encoder ([`AnimatedGifEncoder`](../Sources/Core/Pix2d.Core/Plugins/ImageFormats/GifFormat/Exporters/Gif/AnimatedGifEncoder.cs)) previously ran the `NeuQuant` quantizer **per frame** and wrote a **local color table per frame**, so identical colors drifted frame-to-frame and pixel-art shades flickered. It now builds **one palette shared by the whole animation** (Global Color Table, no local tables): if the animation fits the palette budget its colors are used **verbatim** (no quantization — exact fidelity), otherwise a single NeuQuant pass over all frames combined produces one shared reduced palette; transparency slot reserved only when actually used. Verified end-to-end (structural: 0 local color tables in all paths; round-trip: SkiaSharp `SKCodec` decodes every frame byte-exact). **Remaining:** **APNG** export and sprite-sheet-per-tag.

### H2.6 Drawing workflow parity `P2`
- [x] **Fill-tool opacity** — the paint bucket poured a flat, always-opaque color; the brush has had an Opacity slider for ages, so the fill panel now carries the same control (1–100 %, `SliderEx`, next to the existing Erase-mode toggle in [`FillToolSettingsView`](../Sources/Core/Pix2d.Core/Plugins/Drawing/UI/FillToolSettingsView.cs)). **Semantics match the brush**, deliberately: opacity *scales the fill color's alpha* and the region is composited `SrcOver`, so a 50 % red over opaque blue blends to purple rather than replacing it with half-transparent red — one meaning of "Opacity" across every tool. In erase mode the same number scales the `DstOut` mask, i.e. a partial erase. **Plumbing:** the value lives on `IDrawingLayer.FillOpacity` (0..1, clamped), not on the tool — the fill happens in `PointerInputRouter.TryApplyFillOnRelease`, deep in the pointer pipeline, which only ever sees the drawing layer; `FillTool.Opacity` is a percent facade over it, the same shape as `PixelSelectColorTool.Tolerance` → `ColorSelectionTolerance`. Per-tool, not persisted. A zero-opacity fill is swallowed instead of pushing an undo step for a no-op. **The real bug this uncovered:** [`FloodFiller.GetPixelBytes`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Common/FloodFiller.cs) wrote straight RGBA into the drawing layer's `SKAlphaType.Premul` working bitmap. That was invisible while every fill was opaque (premultiplying by α=255 is the identity) but renders over-bright the moment α < 255 — the channels are now premultiplied there. **Covered by ScenarioTests** (140/140 green, up from 135): percent↔0..1 mapping and clamping, a full-strength fill still flooding the whole canvas opaque, a 50 % fill on an empty canvas landing at α≈128, a 50 % fill over opaque blue blending to ~(127,0,127,255) — *this is the premultiply regression test; without it the red comes back at 255* — a half-strength erase halving alpha, and a 0 % fill changing neither pixels nor the undo stack. **Verified on a running Debug build** through the AgentTools inspector: fill panel renders the OPACITY band + Erase toggle, scrubbing the slider to 40 updates the readout, and a 40 % fill on a fresh tab leaves the transparency checkerboard visible through the paint.
- [x] **User brush presets** — save the current brush settings as a preset tile, delete any preset (a user preset for good, a built-in one hidden and restorable), capture the current pixel selection as a new stamp preset, reset the whole row back to the shipped defaults; persisted across restarts on every head. Modeled on the H2.3 palette library where the analogy actually holds, and deliberately *not* where it doesn't: a brush preset is one item, not a named set, so the existing preset row *is* the library — there is no name prompt, no second-level "load a saved set" step, just Save/Delete/Reset. **Model:** `BrushSettings` gains `IsUserPreset` (a saved preset vs. a built-in) and `BuiltInId` (a built-in's permanent slug, e.g. `"circle-6"`, assigned once in `DrawingService.BuildBuiltInPresets` and never renumbered — deriving it from scale/opacity instead would let a later release's retuning silently un-hide a preset the user removed); both collapse to a serializable [`BrushPresetData`](../Sources/Core/Pix2d.Shared/Primitives/Drawing/BrushPresetData.cs) via a stable brush-type key ([`BrushKeys`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Brushes/BrushKeys.cs): `square`/`circle`/`spray`/`marker`, plus `BrushKeys.StampKey` for a captured selection) so a class rename can't orphan a saved preset — the same discipline `NodeTypeRegistry` applies to node types, at a fraction of the machinery. Both `IsUserPreset` and `BuiltInId` are deliberately excluded from `Equals`/`GetHashCode` (equality means "draws the same"; provenance isn't part of that). **Storage:** `AppSettings.UserBrushPresets` (mirrors `SavedPalettes`) plus a new `AppSettings.HiddenBuiltInPresetIds` (a plain `List<string>` of removed built-ins' `BuiltInId`s) — still no files, no cross-editor interchange format, file import/export stays a non-goal. `DrawingService.BuildBuiltInPresets` builds the built-ins in code (never persisted, so they stay free to evolve between releases) and filters out anything in the hidden-ids list; `InitBrushSettings`/`LoadUserPresets` then append the stored user presets, resolving each through `BrushKeys` (or, for a stamp, decoding its embedded PNG) and clamping scale/opacity/spacing — an unknown brush key, a corrupt stamp image, or an out-of-range value from a hand-edited or future-build settings file is skipped/clamped rather than thrown. **Stamp presets:** [`ImageStampBrush`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Brushes/ImageStampBrush.cs) captures the active pixel selection's bitmap (`IDrawingLayer.GetSelectionLayer()`, downscaled to a 128px-long-side cap before storage — `SettingsService.Set` re-serializes the *whole* settings file on every write, so an uncapped capture would balloon it) and, unlike every procedural brush, belongs to exactly one preset rather than being one of `DrawingService.Brushes`' shared singletons — `BrushPresetData` embeds its source bitmap as a base64 PNG instead of resolving a type key. Two color modes, both reachable as separate presets-menu items and both persisted/restored the same way: **original colors** reproduces the captured pixels as a decal (the paint color is ignored), **recolorable** treats the capture as an alpha mask tinted by the paint color, i.e. behaves like every other brush. Aspect ratio is preserved on resize (the longer side follows the Size slider, matching every brush's "Scale is a literal pixel length" contract; the shorter side scales proportionally) with nearest-neighbor resampling so a resized stamp stays pixel-crisp. Because it is the one brush with per-instance data, it is also the one brush a `new()` can't reproduce — the settings panel's stroke preview must run on a throwaway copy (`RenderStrokePreview` mutates pressure + the stamp cache, and presets *are* the singletons the canvas draws with), and getting that copy from `Activator.CreateInstance(brush.GetType())` threw `MissingMethodException` the instant a stamp preset was selected. Copies now come from a virtual `BasePixelBrush.CreatePreviewInstance()` — reflection for the four procedural brushes, an explicit non-owning copy for a stamp, which shares the captured bitmap (the preview re-renders on every slider tick) but doesn't dispose it, so disposing the copy leaves the preset intact. **Service:** `IDrawingService` gained `CreateBrushPresetFromSelection(useOriginalColors)` and `ResetBrushPresetsToDefaults()` alongside the existing `SaveCurrentBrushAsPreset`/`DeleteBrushPreset`. `SaveCurrentBrushAsPreset` dedupes against an existing value-equal preset instead of ever duplicating (now also accepting an `ImageStampBrush`-backed current brush, not just the four procedural types) and reassigns `SpriteEditorState.BrushPresets` to a new list rather than mutating in place — `StateBase` watchers fire on assignment, not on list mutation. `DeleteBrushPreset` now acts on **any** preset and always removes **by reference** (never the value-equality `List.Remove` would use, since a user preset can be a value-twin of a built-in): a user preset is dropped for good and re-persisted; a built-in is only added to `HiddenBuiltInPresetIds` so `ResetBrushPresetsToDefaults` can bring it back — which it does by rebuilding the built-in row from code while splicing in the *existing* (not reloaded) user-preset objects, so a selected user preset stays selected across a reset. **UI:** the `BrushSettingsView` presets-menu `MenuFlyout` grew from two items to six (Save current / Save selection ×2 color modes / Delete / Reset), the two "save selection" items gated on `IDrawingLayer.HasSelection` (kept live via its `PixelsSelected`/`SelectionRemoved` events — the popup is created once and toggled via `PopupView.IsOpen`, never re-created, so one subscription needs no matching unsubscribe), Delete's confirmation wording branches on whether the target is a user preset (irreversible) or a built-in (mentions Reset brings it back). en + ru localized. **Explicitly cut:** file import/export, a name prompt (the tile *is* the name), undo/redo (brush presets are app-level state, not per-project undo history — same reasoning as the palette library), a `+` tile / long-press-delete / canvas-overlay affordance beyond the menu, per-built-in "un-hide" (only the row-wide Reset restores a hidden built-in). **Verified headlessly:** the ScenarioTests brush-preset scenario now covers hide-a-built-in → persisted to `HiddenBuiltInPresetIds` → `ResetBrushPresetsToDefaults` restores it without touching the one user preset present, no-selection yields no stamp preset, an original-colors stamp round-trips through settings and repaints its captured color while ignoring the active paint - [x] **Custom brushes in the shape tools** — Line / Rectangle / Oval / Triangle already stamped `IDrawingLayer.Brush`, so picking a spray, marker or captured image stamp and drawing a shape *looked* supported, but three defects made every non-default brush behave differently in a shape than under the pencil. **(1) Soft-brush opacity vanished.** A `Marker` brush is an even-opacity brush: its dabs union into the stroke buffer at full strength and the whole stroke is composited once at the brush opacity. That composite (`DrawingLayerNode._strokeBufferOpacity`) was armed only for `BrushDrawingMode.Draw`, and shapes run in `ExternalDraw` — so a 50 % marker rectangle came out solid. The gate now covers both modes (smoothing stays freehand-only: it reshapes a cursor path, which a shape does not have), and the copy-on-write display snapshot that shape previews publish on every pointer move goes through the same composite, so the preview and the committed result finally agree. **(2) Ovals stamped the brush at its size squared.** [`StrokeRenderer`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Nodes/StrokeRenderer.cs)'s `DrawPoint` forwards its 4th argument to `IPixelBrush.Draw`'s **`pressure`**, which *multiplies the stamp scale* — and `DrawEllipse` was passing `brush.Size` there, so a size-5 square brush stamped 25 px blobs, offset by the un-scaled center point (Circle/Marker/Spray hid it by pinning pressure to 1 in their own `Draw` override; Square and every image stamp did not). The parameter is renamed to `pressure` at the definition so the trap reads as what it is. **(3) Dab spacing leaked between shapes and between preview frames.** Spacing is measured from the previous dab and that state outlived the stroke, so a shape drawn near the previous one had its opening dabs swallowed — with a wide spacing the whole shape vanished — and since a shape re-rasterizes its entire outline on every pointer move, the dab phase shuffled while dragging and the committed shape was not the one previewed. New `IPixelBrush.BeginStroke()` drops that state; `BeginDrawing` and each of `DrawLine`/`DrawRect`/`DrawEllipse` call it per pass. **Also:** the ellipse rasterizer now collects its outline and walks it in perimeter order instead of stamping the midpoint loops' four mirrored points as they are emitted — consecutive dabs used to jump across the ellipse, which made spacing (and an image stamp's phase) meaningless on an oval; the point set is unchanged, so a 1 px brush draws the same pixels, and de-duping the quadrant seams stops a semi-transparent brush double-darkening those four pixels. No UI change was needed — the brush picker is gated on the Sprite context, not on the pencil tool. **Covered by ScenarioTests** (157/157, sweep 78 executed / 0 findings): line thickness follows the brush, a 0.5-opacity marker line lands at α≈128, an oval's painted bounds stay within a stamp's radius of its outline, an image stamp paints its own captured colors along a line, and a short shape drawn next to the previous one still paints its start point. **Verified on a running Debug build** through the AgentTools inspector: the held line preview shows the checkerboard through a 50 % marker stroke and the committed pixels read a uniform `#d3681e7f`, and a marker oval renders as an even-toned ring at the nib's own size with no seams and no oversized blobs.
- [x] **Fix: shapes drew nothing on any artboard except the one at the world origin** — reported against a real 23-artboard project, where Line / Rectangle / Triangle simply did not draw. **Two coordinate spaces meet in [`StrokeRenderer`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Nodes/StrokeRenderer.cs) and nothing said so.** The freehand pipeline feeds **world** points (`PointerInputRouter` passes `Pointer.WorldPosition` straight through), so `DrawStroke` maps them through the inverse global transform. The shape builders feed **layer-local** points — `PixelShapeTool` resolves the pointer with `GetPosition(drawingLayer)` before handing it to the builder — and `DrawLine`/`DrawRect` funnelled into that same world-space `DrawStroke`, mapping a second time. The drawing layer's adorner sits at the sprite's global position ([`AdornerLayer.GetAdornerLayer`](../Sources/Core/SkiaNodes/CommonNodes/AdornerLayer.cs)), so the outline was shifted by the artboard's world offset and landed off-canvas — exactly zero pixels, silently. At world (0,0) the transform is the identity, which is why this survived: the first artboard of every project, and every scene the harness had ever built, worked fine. Split into `DrawStroke` (world, maps) and `DrawStrokeLocal` (layer-local, the actual rasterizer); every entry point now states its space in its doc comment. `DrawEllipse` was the one that already treated its input as local — which is why the Oval tool alone kept working on offset artboards — and is now labelled rather than "corrected" into the bug. **Regression-tested properly:** the harness's default project has a single sprite at the origin, so the new ScenarioTests checks add a second artboard, *assert that the drawing layer's global transform actually carries the offset* (otherwise they would pass vacuously), and cover line / rect / triangle / oval; confirmed to fail 3/4 with the fix reverted and a forced rebuild. **Verified on a running Debug build**: a line on an artboard at world (80,0) now commits `#d2691eff` along its row.
- [x] **Fix: the brush cursor stopped following the pointer in every shape tool** — `DrawingLayerNode.OnPointerMoved` updates `PreviewPosition` and then returns early for `BrushDrawingMode.ExternalDraw` (there is no stroke to advance — the tool drives the drawing), but the early return also skipped the `Refresh()` at the bottom. The node still owns the brush cursor overlay, so the cursor sat frozen wherever it was last painted and only caught up when something unrelated invalidated the viewport — which, on a multi-artboard scene, meant crossing an artboard boundary. Now refreshes when the preview is visible and the position actually changed. **Verified on a running Debug build**: hovering across the canvas with the Line tool moves the stamp outline continuously.
- [x] **Ctrl+click a layer thumbnail selects that layer's opaque pixels** — [#57](https://github.com/gritsenko/Pix2d/issues/57) (`enhancement`, `selection`). "Load layer transparency as a selection", the Photoshop gesture, and the cheapest way to get a marquee that follows artwork instead of a rectangle. New [`OpaquePixelSelector`](../Sources/Core/Pix2d.Core/Plugins/Drawing/PixelSelectors/OpaquePixelSelector.cs) — shaped like `SameColorSelector`'s whole-layer pass (full-bitmap mask + `Algorithms.GetContour`) but keyed on alpha, so it needs no seed point; alpha is the 4th byte in both `Rgba8888` and `Bgra8888`, so it needs no color-type branch either. Reached through `IDrawingLayer`/`IDrawingService.SelectOpaquePixels(mask)` → `SelectionController.SelectOpaquePixels`, which is the one place that owns the semantics: **the mask is a parameter, not the drawing target**, so the silhouette of one layer masks edits on another (the whole point of the gesture — the tile click deliberately does *not* change the active layer); a mask that doesn't match the target's size, or a `null` one (a layer whose current frame has no pixels allocated yet), selects **nothing** rather than doing nothing, because the gesture always *replaces* the selection. `FinishSelection` gained an optional highlight override so this path always traces a contour — unlike the marquee tools it has no rectangle to fall back on. The gesture then activates `PixelSelectRectTool` exactly as `Edit.Selection.SelectAll` does, and `DrawingService` applies the user's auto-open-transform preference on top, so the marquee lands in the same state as a hand-drawn one. Modifier detection is recorded on **pointer-down** (`Click` fires on release and `RoutedEventArgs` carries no modifiers) and accepts Cmd as well as Ctrl. **Covered by ScenarioTests** (174/174, sweep 78 executed / 0 findings): the marquee matches the 3×3 painted block rather than the canvas — which is what makes the check discriminating, since ignoring the mask degrades to Select-All — the active layer is untouched, the tool is a selection tool, and an empty layer drops the previous marquee without making a new one. **Verified on a running Debug build** via the AgentTools inspector.
- [x] **Layer titles: rename, and show the name on the tile** — [#67](https://github.com/gritsenko/Pix2d/issues/67) (`Feature`). Layers had names in the document model (`Layer 000`, …) but no way to change one and nowhere they were displayed, so a stack of look-alike thumbnails was all the organization on offer. **Rename** is a button in the layer-options popup (next to Delete/Clear/Clone/Merge/Up/Down) → `IDialogService.ShowInputDialogAsync` → new `SpriteEditor.RenameLayer`, which is **undoable** via a new generic [`RenameNodeOperation : ChangeNodePropertyOperationBase<string>`](../Sources/Core/Pix2d.Shared/Operations/RenameNodeOperation.cs) — unlike the artboard rename, which mutates a scene object outside the sprite editor's history. A blank name is rejected instead of stored (an empty caption is worse than none) and `LayersView` refreshes the tile off `OperationInvokedMessage` so undo/redo of a rename — which changes no pixels — still updates the caption. **Display:** the tile grew a name strip *below* the 80×80 thumbnail rather than overlaid on it — insetting the icon column by a strip's height clips the 18pt glyphs — and the strip is **present only when the user actually named the layer**: `Pix2dSprite.IsGeneratedLayerName` matches the auto-generated *pattern* (`Layer <n>`, not "the name it would get right now", since reorder renumbers layers), so an unnamed tile keeps its original 80×80 and a caption reading "Layer 003" never appears. Long names ellipsize with the full name on the tooltip; the blend-mode marker deliberately stayed over the artwork instead of sharing the strip, where a word like "Luminosity" would have squeezed the title to two characters. en + ru localized. **Covered by ScenarioTests** (rename writes/undoes/redoes as one step, blank and dismissed prompts are no-ops, the prompt is seeded with the current title, and the tile shows a real name but neither a generated one nor one generated for another index) and **verified on a running Debug build**.
- [x] **Fix: a newly created brush was selected but never activated** — creating a preset from the presets menu highlighted the new tile while every stroke kept using the *previous* brush, in both stamp color modes (colors and recolorable) and when saving the current brush. Cause: "selected" is two pieces of state — `SpriteEditorState.CurrentPixelBrushPreset` is the row's highlight, `CurrentBrushSettings` is what the canvas draws with — and the menu handlers in [`BrushSettingsView.State`](../Sources/Core/Pix2d.Core/UI/BrushSettings/BrushSettingsView.cs) wrote only the first. Tapping a tile sets both via `OnCurrentPixelBrushPresetChanged`, but that handler cannot fire on this path: writing the state property runs `SyncFromDrawingState`, which assigns the view-model property with `_isSyncing` set — precisely the case it bails out of. Both handlers now go through one `ActivatePreset` helper that sets the live brush (to a *clone*, so later slider tweaks don't rewrite the saved tile) as well as the highlight. Activation deliberately stays in the view-model: `IDrawingService.CreateBrushPresetFromSelection`/`SaveCurrentBrushAsPreset` create and persist, they don't change what is active. **Regression test** in ScenarioTests (141/141, up from 140) drives `BrushSettingsView.State` directly — its state is plain, no Avalonia types — and asserts the row highlight *and* `CurrentBrushSettings.Brush` both point at the new preset for both color modes; it fails on the pre-fix code.
- [x] **Additive / subtractive selection (Shift, Ctrl)** — [#49](https://github.com/gritsenko/Pix2d/issues/49). Every marquee used to *replace* the last one: `BeginSelection` applied the previous selection and started from scratch, and the code had no notion of add/subtract at all (`PixelSelectionMode` says *how the region is described* — Rectangle / Freeform / SameColor — never what to do with it). Building a selection out of several strokes, or biting a piece back out of one, was simply not expressible. **The modifiers**, resolved per gesture at pointer-down in [`PointerInputRouter.ResolveCombineMode`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Nodes/PointerInputRouter.cs) into the new [`SelectionCombineMode`](../Sources/Core/Pix2d.Shared/Primitives/Drawing/SelectionCombineMode.cs): **Shift = add, Ctrl = subtract, Shift+Ctrl = intersect**. Photoshop puts subtract on Alt; here Alt is unavailable — `ShouldIgnorePointerPressed` swallows Alt presses for the eyedropper — so it moves to Ctrl. The mode is captured at press and held for the whole gesture (a deferred touch selection promotes several events later, and releasing Shift mid-drag must not turn an add into a replace); with nothing selected any modifier degrades to a plain marquee. **The hard part is that a selection has two representations and only one of them can be combined:** the live one is a `SpriteSelectionNode` carrying lifted pixels, a traced contour and its own transform, and the flat one is a canvas-sized `byte[]` mask. New [`SelectionMaskOps`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Common/SelectionMaskOps.cs) owns the round trip — `Rasterize` (live → mask, honouring the transform, so a marquee the user has already dragged around combines from where it *is*) → `Combine` (the set algebra) → `BuildRegion` (mask → selection layer + background + contour) — and `IPixelSelector` gained `GetSelectionMask(width, height)` so all five selectors (rect/lasso, magic wand, select-all, layer-transparency, AI object) hand back a canvas-space mask instead of each exposing its own private bounding box and offset convention. [`InvertSelectionOperation`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Operations/InvertSelectionOperation.cs), which was doing the same round trip inline, now calls into it — invert is just the negation. **Three things this had to get right beyond the algebra.** (1) *You can see what you are combining with:* the press drops the live marquee before the new one is drawn, so `SelectionMarqueeOverlayNode` also renders the base region's outline, static, for the duration of the gesture. (2) *A subtract drag starts inside the selection*, where the frame's move thumb would otherwise capture the press and move the marquee — new `MoveThumbNode.PassSelectionCombinePressThrough` (sibling of the object tool's `PassShiftPressThrough`) lets a Shift/Ctrl press fall through to the selection tool, enabled only while the marquee is contour-only, since with pixels lifted Shift is the transform's aspect lock. (3) *Undo steps back one region, not all of them:* `BeginSelectionOperation` now takes the selection the marquee was combined with and restores it, so building one up region by region doesn't collapse on the first Ctrl+Z. A combining gesture that produces nothing — Shift+click, or a pinch that interrupts the drag — puts the base selection back rather than clearing it, which is what makes Shift+click a no-op instead of the opposite of what it asks for. **Also:** switching between pixel-selection tools now keeps the marquee (`PixelSelectToolBase.Deactivate` gates on `IToolService.IsSelectionTool` rather than naming `PixelTransformTool`/`CropTool` explicitly), which is what makes rectangle-then-lasso combining reachable at all. **Two latent bugs fell out of it, both invisible until a selection region was rasterized rather than stroked:** `SelectionPath` is stored in canvas coordinates while the layer transform maps from selection-local space, so applying the transform to it landed the region at *twice* its offset — the marching-ants renderer normalizes the path to its own bounds first ([`LineHighlightNode`](../Sources/Core/Pix2d.Shared/CommonNodes/LineHighlightNode.cs)) and `Rasterize` now does the same; and a traced contour set carries holes as separate sub-contours with no guaranteed winding, so it must be filled even-odd or a hole fills solid. Both affected **Invert Selection on any non-rectangular selection** (lasso, wand, layer transparency) before this change — a rectangle marquee has no path, which is what hid it. **Covered by ScenarioTests** (190/190, up from 178; sweep 78 executed / 0 findings): 12 checks asserting the resulting *mask* rather than its bounding box (a union and the rectangle enclosing it have identical bounds, and a subtracted hole has none) — union of two disjoint squares, subtract, intersect, a punched hole surviving a further add, subtracting a selection out of existence, Shift+click preserving the selection, modifiers degrading with nothing selected, rect→lasso across a tool switch, magic-wand Shift+click unioning two colour regions, undo landing on the previous selection, and invert being the exact complement; all run on a second artboard so the target is away from the world origin. **Verified on a running Debug build** through the AgentTools inspector: the base outline is drawn under the in-progress marquee, a Shift+drag commits as one merged contour (21×21 badge over the two overlapping squares), a Ctrl+drag *started inside the selection* subtracts instead of moving it, and Ctrl+Z restores the union. **Not covered:** touch/pen heads have no modifier keys, so this is desktop-only until a combine-mode toggle lands in the selection tool's settings bar — worth doing, and deliberately out of scope here.
- [x] **Adjustable symmetry axes, and radial symmetry** — [#23](https://github.com/gritsenko/Pix2d/issues/23) (`Feature`, `UX/UI`) + [#214](https://github.com/gritsenko/Pix2d/issues/214) (`android`, `Feature`). Mirror drawing existed as two toolbar toggles whose axes were nailed to the middle of the canvas, drawn nowhere, and — with both on — produced **one** extra dab, a 180° rotation about the centre rather than the four images "Mirror X *and* Mirror Y" promises. All three are the same defect: there was no model of a symmetry, only two booleans and a hard-wired `Size.Width - x` in [`StrokeRenderer`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Nodes/StrokeRenderer.cs). **One model now covers everything** ([`SymmetrySettings`](../Sources/Core/Pix2d.Shared/Primitives/Drawing/SymmetrySettings.cs)): N mirror axes through a movable centre, evenly spaced over 180°, the first rotated by an angle. N axes generate the dihedral group D(N) — 2N images — so the presets are points in the same space (X = 1 axis at 0°, Y = 1 axis at 90°, X+Y = 2 axes at 0° = four images) and Maximkaaa's suggestion from #23's thread, radial symmetry for stars and flowers, is the same code at N ≥ 3. **The geometry that had to be right:** a dab's anchor is the brush's `PixelOffset`, which for an even brush size is *not* the middle of the stamp, so [`SymmetryMath`](../Sources/Core/Pix2d.Shared/Primitives/Drawing/SymmetryMath.cs) reflects the **footprint centre** in continuous canvas coordinates and converts back — reflecting the anchor would drift a wide brush off its own axis by half its size. For an axis-aligned axis this reproduces the legacy `Width - x - size + 2*offset` formula bit-exactly (the old code *was* this computation with the centre hard-wired), so the X/Y presets draw the same pixels they always did. Images are de-duplicated, which the old path never did: a dab sitting on the axis used to be stamped twice and double-darkened under any brush below full opacity. The transform set is rebuilt only when the settings or the canvas change — `GetImageAnchors` runs once per rasterized pixel — and the stamp bitmap itself is never rotated (that would need a resample; every built-in brush is symmetric). **On canvas:** [`SymmetryOverlayNode`](../Sources/Core/Pix2d.Core/Plugins/Drawing/Nodes/SymmetryOverlayNode.cs) is a child of the drawing layer, so it inherits its coordinate space and sees a press before it does. It draws the axes clipped to the canvas at screen-constant width, a small non-interactive cross on the intersection, and **one grip parked just outside the canvas** where the first axis leaves it. The grip's placement is load-bearing: the axis lines can't be hit targets (they run through the middle of the artwork and would silently eat strokes) and neither can the intersection — the first cut put a disc there, which defaults to the centre of the canvas, and the regression check for a moved centre painted 0 pixels instead of 2. Drag it to move the axes (half-pixel steps, so an odd-width canvas can be symmetric about a pixel rather than a seam), double-click to re-centre. **The pointer turns into a grab hand over it**, which is the only affordance saying the axes move at all — it sits on empty canvas background where nothing else suggests it. That needed a way for the scene graph to influence the host control's cursor, since the whole canvas is one Avalonia control: new `SKNode.GetHoverCursor(worldPos)` → platform-neutral [`SKCursorType`](../Sources/Core/SkiaNodes/Interactive/SKCursorType.cs), resolved topmost-first by `SKInput.SetPointerMoved` into `SKInput.HoverCursor` and mapped to a real cursor by `SkiaCanvas.UpdateCursor` (below pan and the Alt colour-picker, which are modes the user explicitly asked for). Resolved in the move dispatch rather than from `OnPointerEnter`/`Leave`, because that pass walks the *whole* chain under the pointer unless someone handles the event — so a node gets Enter and Leave within one move as soon as anything interactive sits beneath it. Any draggable node can opt in the same way; the frame thumbs still don't. **State** is `AppState.SpriteEditorState.Symmetry`, session-only and deliberately not in the project file — the same lifetime the Mirror toggles always had — pushed into the drawing layer by `IDrawingService.SetSymmetry`/`SetSymmetryCenter` and re-pushed whenever the layer or its target is rebuilt (project load, tab switch, artboard switch), with a moved centre clamped into whatever canvas it lands in. **UI:** the two Mirror toggles collapse into one `SYMMETRY` button — a click toggles (the old gesture), a **press-and-hold** opens [`SymmetrySettingsView`](../Sources/Core/Pix2d.Core/UI/SymmetrySettingsView.cs) with the three presets, Axes and Angle sliders and a re-centre button. Long-press rather than `ContextFlyout` because Pix2d binds the right mouse button to the eyedropper app-wide, so the platform gesture never arrives (confirmed on a running build — a right-click just switched tools); it is also exactly what #214 asked for, and behaves the same under mouse, pen and touch. en + ru localized. **Covered by ScenarioTests** (210/210, up from 190; sweep 78 executed / 0 findings): the geometry half drives `SymmetryMath` directly — a wide brush centred on the axis producing *no* second stamp, a dab on a half-pixel axis not double-stamped, 2N distinct images for every N up to 12, clamping, axis-segment clipping — and the pipeline half asserts painted-pixel counts through the real drawing layer, where "X+Y paints four pixels" is the check that separates the new behaviour from the old. **Verified on a running Debug build** via the AgentTools inspector: the axes render with their grip, a hold opens the flyout, its X+Y preset commits a stroke at `x=10/53 × y=20..24/39..43` (four copies, 20 px), *Centre the axes* clears the moved centre, dragging the grip 90 DIP left moves the mirror to `x=32`, and `SkiaCanvas.Cursor` reads `Hand` over the grip and `Arrow` over the artwork on either side of it. That pass also caught a live-only bug of its own — opening the flyout takes the pointer capture, so the release that ends a long press does not always raise `Click`, and the "don't toggle after a hold" flag stayed armed and swallowed the user's next deliberate click; it is now disarmed on every press. **Not done:** the axis angle has no on-canvas rotation handle (the slider is the only way to set it), and a rotated axis maps dab centres by rounding, so radial symmetry on a small canvas is approximate by nature.
- [x] **Fix: `pix2d_state` always reported `pixels=False` for the pixel selection** — `SpriteEditorState.HasSelection` was a state property nothing ever assigned, and both AgentTools summaries read it, so an agent verifying selection work was told there was no selection with a marquee plainly on screen (it cost a chunk of this feature's verification pass before the reporting, not the code, turned out to be wrong). Both now read `IDrawingService.DrawingLayer.SelectionPhase` — which also distinguishes a contour marquee from lifted pixels — and the dead property is gone (H1.3).

Sentry sinks (desktop + Android) set `CacheDirectoryPath`, so a fatal crash captured while the host is down is persisted locally and re-sent on the next launch.
- [x] Unified telemetry consent (strict opt-in): a single `TelemetryConsent` (was crash-only `CrashTelemetryConsent`; legacy value migrated) now gates **both** analytics AND crash reporting. Nothing is sent until the user allows it. A crash-independent first-launch consent dialog (`TelemetryConsentDialogView`) is shown once when consent is `Unset` on a telemetry-supported platform; a pending crash still routes to `CrashReportDialogView` (its toggle collects the same consent) so the two never stack. `ICrashReportService.TelemetryConsentChanged` lets the bootstrapper bring analytics + the Sentry sink up the instant consent flips to Allowed, without a relaunch. Fixed the phantom "empty" crash dialog on desktop first launch: desktop now marks a clean exit in `OnAppClosing`, and the interrupted-launch heuristic no longer manufactures a content-free report when there's no OS exit verdict and no `Fatal.log`. A Settings toggle (`AppSettingsView` → "Anonymous telemetry") lets the user review/withdraw consent any time — flipping it off flushes and unregisters the AppStat target (`Logger.UnregisterLoggerTarget`) so collection stops mid-session, not just next launch. The first-launch consent prompt covers **Android + desktop + WASM** (the prompt has no crash-sink dependency; WASM keeps crash reports manual-only but browser analytics is opt-in-enabled), so no platform silently loses analytics under the opt-in model. **Hotfix (3.8.1):** the consent dialog crashed at Android startup on windowed/resizable devices (ChromeOS) — a config-change rebuild of `MainView` replaced the `DialogContainer` while a dialog view was still parented in the old one, throwing "already has a visual parent ContentPresenter". `AvaloniaDialogService.SetDialogContainer` now drops the stale current/queued dialogs on container replacement, and `DialogContainer.ShowDialog` detaches a view from any prior parent before re-hosting it.
- [x] **Active session time telemetry** `P2` — the dashboard's "Avg. session" (6h+!) was Sentry release-health wall-clock (process alive, incl. minimized/backgrounded), not real usage. **Shipped** per design [docs/active-session-telemetry.md](active-session-telemetry.md), spanning both repos. **Client:** [`ActiveTimeTracker`](../Sources/Core/Pix2d.Infrastructure/AppStat/ActiveTimeTracker.cs) — a monotonic-clock accumulator that counts only foreground + non-idle time (5-min idle lease, settle-on-signal, no internal timer); [`ActiveSessionLifecycleHost`](../Sources/Core/Pix2d.Core/Services/Telemetry/ActiveSessionLifecycleHost.cs) feeds it Avalonia signals (desktop `Window.Activated/Deactivated`, mobile `IActivatableLifetime`, tunnel input handlers on `TopLevel` re-attached on `ViewPortInitializedMessage`); [`SessionStatsReporter`](../Sources/Core/Pix2d.Core/Services/Telemetry/SessionStatsReporter.cs) pushes cumulative `@session` pings every 5 min (skipped when active time didn't grow) over the existing `AppStatLoggerTarget`/`/api/track` transport, forced-flushed on desktop `OnAppClosing`, Android OnPause/OnStop + double-back exit, and consent withdrawal. Tracker is consent-independent (inert until the consent-gated reporter reads it); Sentry `AutoSessionTracking` untouched (still the crash-free-rate source). **Server (AppStatServer):** `@session` pings intercepted at `/api/track` → [`ClientSession`](../../AppStatServer/src/AppStatServer/Data/ClientSession.cs) max-merge upsert (cumulative counters ⇒ duplicate/out-of-order-safe; verified by smoke test), joined to its `TrackEvent`s by `SessionId`; analytics adds active avg/median, wall median, engagement ratio, and an active-time histogram; new `GET /api/client-sessions[/{id}]` endpoints; dashboard shows median-active-first tiles, a "Session engagement" row (engagement %), dual wall/active histograms, and a recent-sessions table with per-session event-timeline drill-down (plus a Maintenance self-test button). Reserved `@`-prefixed events are filtered from all product reports.
- [x] **Automate the Store submission** `P3` — packaging is automated ([`release-publish.yml`](../.github/workflows/release-publish.yml)) but the resulting `.msixbundle` was still dragged into Partner Center by hand every release, because the previous automation *silently published the wrong thing*: the retired StoreBroker job (`upload-to-store` in `dotnet-desktop-winstore.yml`, deleted in f11409d) created a submission, uploaded the package and committed — and the update that went live carried the **previous release's** packages. Root cause is two independent bugs in how it drove the v1 submission API, both confirmed against the docs: (1) `Update-ApplicationSubmission` leaves a cloned submission's packages untouched unless `-AddPackages`/`-ReplacePackages` is passed, so setting `ApplicationPackages = @()` in the JSON was a no-op; (2) the SAS `fileUploadUrl` expects a **ZIP whose entries match `applicationPackages[].fileName` with `fileStatus=PendingUpload`**, not a bare `.msixupload` (`Set-SubmissionPackage` only PUTs the file you hand it). *The API itself never changed* — MSIX still submits through `manage.devcenter.microsoft.com/v1.0/my/applications/…`, with no deprecation notice; what changed is the tooling Microsoft documents ([msstore CLI](https://learn.microsoft.com/windows/apps/publish/msstore-dev-cli/github-actions), actively developed, vs StoreBroker which is legacy and no longer referenced from the docs). The v2 API (`/submission/v1/product/…`) is **MSI/EXE only** and explicitly not for MSIX, so there is nothing to migrate to. **Shipped** (final shape — the two intermediate designs and why they were wrong are recorded below): `microsoft/microsoft-store-apppublisher@v1.1` → `msstore reconfigure` → `msstore publish <bundle> -id 9NBLGGH1ZDFV` as a single command. The CLI performs the whole clone → declare packages → zip → upload → commit dance itself, and since [Dec 2025](https://github.com/microsoft/msstore-cli/commit/311d3d20) also marks superseded packages `PendingDelete` (which is what the old job's empty-array hack was reaching for). Constraints encoded in the workflow comments: needs a new `SELLER_ID` secret (StoreBroker didn't use one) and the Manager role on the Entra app; msstore [hard-refuses non-free products](https://github.com/microsoft/msstore-cli/issues/115) (`pricing.priceId == "Base"` → aborts *and deletes the draft*) — Pix2d is free (DisplayCatalog reports `listPrice 0.0`), so it passes; and an API-created submission must never be touched by hand in Partner Center or it can no longer be committed via the API. **Dry run passed (2026-07-27, submission `1152921505701500952`, `version=3.11.3`):** submission created → `Pix2d_3.11.3.0_x64_arm64.msixbundle` zipped, PUT accepted (200) and uploaded to `ingestionpackagesprod1` → left at `PendingCommit`. The Partner Center UI showed *Packages: Unchanged*, which looks exactly like the StoreBroker failure but isn't — a `PendingUpload` entry has no version/architecture until the commit ingests the ZIP, so the UI keeps rendering the last published set. Proven by reading the submission back with a throwaway read-only probe workflow (`store-submission-inspect.yml`, added in `fb3f231` and deleted once the pipeline was proven — restorable from history; it just ran `msstore submission status/get` and printed the arrays): `Pix2d_3.11.3.0_x64_arm64.msixbundle → PendingUpload` alongside `Pix2d_3.11.2.0_x64_arm64.msixbundle → PendingDelete`. Two things that probe also surfaced: the Store tracks the *bundle's* date-derived `Identity/@Version` (`2026.725.1408.0`) rather than `Pix2dVersion`, and the legacy `.msixupload` packages (3.11.1.0 and older) stay `Uploaded` forever because msstore only supersedes the package sharing the new file's extension. **Commit verified (2026-07-27, submission `1152921505701501667`):** the commit ingested the ZIP and Partner Center listed `Pix2d_3.11.3.0_x64_arm64.msixbundle` as **Validated** — so the API path accepts an **unsigned** bundle exactly like the web upload does, which was the last open question. That run still ended `CommitFailed` with a single `InvalidState` error ("The requested action conflicts with an existing resource. Please refresh the page and try again"), which msstore surfaces as the far more alarming *"active validation errors which cannot be exposed via API"*. It was a concurrency conflict, not a validation problem: the dashboard page for that submission was open in a browser during the commit, and clicking **Submit for certification** on the very same submission afterwards went through cleanly. So: keep the submission closed in Partner Center while the job runs; recovery from a failed commit is just a re-run, since msstore deletes a failed pending submission and creates a fresh one. **That run also exposed a defect in the job itself** — it was structured as `msstore publish -nc` followed by `msstore submission publish`, and the latter returns 0 the moment the commit is *accepted*, so the workflow went green while the submission failed minutes later. Now it is a single `msstore publish` without `-nc`, which polls until the submission leaves `CommitStarted`, prints the `statusDetails` tables and exits non-zero on `CommitFailed`. **End-to-end green on the re-run with the dashboard closed** (run `30296671956`): `Submission Status - PreProcessing` → `Submission commit success!`, and the printed package list shows `Pix2d_3.11.3.0_x64_arm64.msixbundle` with `Pix2d_3.11.2.0_x64_arm64.msixbundle` gone — the supersede-and-replace the StoreBroker job never managed. 3.11.3 went to certification as a **Store-only** build (no `v3.11.3` tag, so the other channels stay on 3.11.2 — the daily `attach-store-msix` is unaffected because `v3.11.2` already carries its store-signed asset; a future full release must not reuse the 3.11.3 number with different content). **Now folded into the release pipeline:** the standalone `windows-store-msix.yml` is gone and its packaging + submission live in `release-publish.yml` as `build_store_msix`, which follows the same rule as `build_android` — a `v*` tag builds *and* submits (the Store equivalent of the automatic Google Play production push), a manual dispatch builds only unless `submit_to_store` is ticked. The Store therefore stops being a separate manual chore in the release checklist.

- [ ] **Cross-platform "rate the app" prompt** `P2` — the prompt heuristics/UI ([`ReviewService`](../Sources/Core/Pix2d.Core/Services/ReviewService.cs) + [`RatePromptView`](../Sources/Core/Pix2d.Core/UI/RatePromptView.cs)) were already cross-platform; only a concrete `IReviewService` was Android-only, so desktop/web never showed it. **Shipped:** `DesktopReviewService` routes by distribution channel — MS Store (MSIX) build → native `StoreContext.RequestRateAndReviewAppAsync` dialog (fallback `ms-windows-store://review/?ProductId=9NBLGGH1ZDFV`); portable / itch.io / Gumroad / Linux / macOS → the `pix2d.com/review` hub (the binary can't know its download channel, so the site — updatable without a release — picks the destination). `IPlatformStuffService.IsStorePackage` gates it; the service is force-constructed at startup so Save/Export triggers are live. **Conversion funnel** logged to appstat (`stats.pix2d.com`) as `*Review:` custom events — `Showing prompt` (banner impression) → `Accepted`/`Dismissed` (banner response) → channel detail (`Store dialog` with `result=Succeeded/CanceledByUser/…`, `Opened store page`, `Opened review hub`, `In-app review requested`); all events share one funnel's context/promptsCount/workTime props via `ReviewService.LogReview`. **Remaining:** (1) build the `pix2d.com/review` hub page that reads `?src/os/pkg/v` and offers MS Store / itch / Gumroad / GitHub-star / Telegram CTAs; (2) `WebReviewService` on the WASM head → same hub (`?src=web`); (3) localize the hard-coded English prompt strings in `ReviewService`; (4) if Pix2d ever ships on the Mac App Store, add a `macappstore://…?action=write-review` branch.
  - **Follow-up (3.11.1, done):** the 2-hour work-time gate in `TrySuggestRate` could never pass — `TotalWorkTime` was only persisted from `SaveTotalWorkTime()`, whose sole caller `Dispose()` is never reached in the real app lifecycle (Android backgrounds/kills via `OnPause`/`OnStop`/`OnDestroy`; desktop's `OnAppClosing` doesn't touch this service either), so the stored value stayed `0` forever. Fixed in [`ReviewService.cs`](../Sources/Core/Pix2d.Core/Services/ReviewService.cs): a new `GetTotalWorkTime()` computes the total live (persisted total + elapsed since `LaunchTime`) instead of relying on a flush point that never fires, and the previous session's elapsed time is folded in at the start of the next one.
  - **Follow-up (post-3.11.1, done) — the whole prompt gate was a no-op, and the settings layer hid it.** Production funnel data from the 3.11.1 Android rollout showed the prompt firing **on a fresh install 1m26s into the first session**, `Accepted` logged **twice** a second apart, the banner **re-shown after the user had already rated**, `promptsCount` stuck at `0`, and the nonsense `workTime=739820+days`. One root cause explains all five: [`ISettingsService`](../Sources/Core/Pix2d.Shared/Abstract/Services/ISettingsService.cs) resolves keys to properties **on `AppSettings` by name** via reflection, and **none of the review-funnel keys were ever declared there** — so every `Set` silently no-op'd and every `Get` returned `default`. `LaunchTime` read back as `default(DateTime)`, making `DateTime.Now - launchTime` ≈ 739820 days, which sails through the 2-hour gate; `IsAppReviewed`/`NextPromptTime`/`AppReviewPromptsCount` never persisted, so nothing could ever terminate or defer the funnel. Fixes: (1) declared all funnel keys in [`AppSettings.cs`](../Sources/Core/Pix2d.Core/Services/AppSettings.cs) (`LaunchTime`, `TotalWorkTimeTicks`, `IsAppReviewed`, `NextPromptTime`, `AppReviewPromptsCount`, `IsInAppReviewShown`) — the cumulative total is stored as `long` ticks rather than a `TimeSpan` so it round-trips through System.Text.Json unambiguously, and all call sites now use `nameof(AppSettings.X)` instead of loose string literals; (2) `GetSessionTime()` treats a missing/`default` `LaunchTime` as *zero* elapsed, so an unwritable settings file leaves the gate **closed** rather than wide open; (3) `RateApp()` is re-entrancy-guarded and owns the `IsAppReviewed` write (it awaits a platform dialog for seconds, and [`WindowCommands`](../Sources/Core/Pix2d.Shared/Commands/WindowCommands.cs) now dismisses the banner *before* awaiting — the live button is what produced the double `Accepted`); (4) `TrySuggestRate` bails when the banner is already on screen, logs the impression *after* the counter increment (so `promptsCount` identifies *this* impression instead of always trailing by one), and applies a 3-day cooldown to an impression the user simply ignores, which previously left no state and re-prompted on the very next save.
  - **Follow-up (post-3.11.1, done) — same bug class, two more dead settings.** Auditing every `ISettingsService` key against `AppSettings` found two more that silently never persisted: **`IsAutoOpenTransformEditorAfterSelectionEnabled`** (the Settings toggle reverted to `true` on every launch) and **`lastUpdateCheckUtc`** (the update-check throttle in [`UpdateService`](../Sources/Core/Pix2d.Core/Services/UpdateService.cs) never held, so it re-checked every launch); both now have properties. To stop this class of bug recurring silently, [`SettingsService.Set`](../Sources/Core/Pix2d.Core/Services/SettingsService.cs) now **logs once per unbacked key** instead of discarding the write without a trace — a silent write loss cost a full release. *Note: the legacy `CrashTelemetryConsent` migration read in `CrashReportService` is dead for the same reason (the key never had a property, so no user ever had it persisted); harmless now that 3.11 is well past that migration, and left unbacked deliberately so it doesn't add a dead field to `pix2d_settings.json`.*

## 10. Non-goals (explicitly out of scope)

- Building/hosting our own image-generation models — integrate providers, never own inference.
- A binary plugin marketplace with payments/DRM — curated list only.
- Vector tools beyond pixel-perfect shape primitives.
