# Pix2D — Long-Term Roadmap

> **Status:** Draft proposal · Last updated: 2026-08-01 · Baseline version: [v3.11.2](https://github.com/gritsenko/Pix2d/releases/tag/v3.11.2)
>
> This document is written for **both humans and AI coding agents**. Each work item includes context, acceptance criteria hints, and reference links so an agent can pick up a task with minimal extra briefing. Read [`CLAUDE.md`](../CLAUDE.md) and [`CONTRIBUTING.md`](../CONTRIBUTING.md) before starting any task. UI work must follow the project skill at [`.claude/skills/pix2d-ui`](../.claude/skills/pix2d-ui).

---

## 1. Vision & Positioning

**Pix2D is the asset pipeline tool for indie game developers: a modern, free, open-source sprite/pixel-art/animation editor that runs everywhere — Windows, Linux, macOS, Android, and the browser.**

Litmus test for every roadmap item:

> *Does this get an artist's asset into a running game faster?*

### Competitive landscape (for context, not imitation)

| Competitor | Strengths | Our differentiation |
|---|---|---|
| [Aseprite](https://www.aseprite.org/) ([source](https://github.com/aseprite/aseprite)) | Industry standard, huge feature set, scripting | Paid, desktop-only, dated UI. We win on: free/MIT, mobile + web, modern UI |
| [Pixelorama](https://orama-interactive.itch.io/pixelorama) ([source](https://github.com/Orama-Interactive/Pixelorama)) | Free, Godot-based, active community | We win on: native performance (SkiaSharp), mobile UX, stylus/pressure support |
| [Piskel](https://www.piskelapp.com/) | Zero-friction web editor | Effectively unmaintained. We win on: everything, once our web version is first-class |
| [LibreSprite](https://libresprite.github.io/) | Free Aseprite fork | Slow development. We win on: velocity, modern stack |

### Strategy in the AI era (2026)

Two real threats: (a) casual users generating assets instead of drawing them, (b) AI-native competitor editors. Two real advantages: (a) generative models are still bad at strict-palette, grid-consistent, animation-consistent pixel art — manual control remains technically necessary in this genre; (b) a solo maintainer with AI agents now matches the output of a small team, while competitors carry legacy codebases.

**Positioning answer:** Pix2D does not compete with generation — it *hosts* it. "AI drafts, human finishes, agent exports." And Pix2D itself becomes a tool that agents can drive (CLI + MCP), making it a node in AI game-dev pipelines rather than a victim of them. See [Track E](#track-e--ai--agent-integration).

## 2. How to read this roadmap (for agents)

- Work is organized into **Horizons** (time-ordered) and **Tracks** (thematic, continuous).
- Priority: `P0` = drop everything, `P1` = next release, `P2` = planned, `P3` = opportunistic.
- Before implementing: check [open issues](https://github.com/gritsenko/Pix2d/issues) for duplicates; link the roadmap item in the PR description.
- Definition of done for any item: code + tests (see [Track Q](#track-q--quality-infrastructure)) + entry in release notes draft + no regression in golden-image tests.
- Tech stack anchors: [Avalonia UI](https://docs.avaloniaui.net/) (currently 12.0.5), [Avalonia.Markup.Declarative](https://github.com/AvaloniaUI/Avalonia.Markup.Declarative), [SkiaSharp](https://github.com/mono/SkiaSharp) (currently 3.119.4), [SixLabors.ImageSharp](https://github.com/SixLabors/ImageSharp), .NET / C#. Web build runs on the Avalonia [WebAssembly backend](https://docs.avaloniaui.net/docs/guides/platforms/how-to-use-web-assembly).

## 3. Horizon 1 — Stabilization & Trust (0–3 months)

Goal: after the large v3.8.0 release, make export/selection/drawing bulletproof. Ship as a series of `3.8.x` patch releases.

### H1.1 Bug burn-down `P0`

The "onion skin on by default / double-click to disable" note in the issue is stale (pre-3.8.0 animation-controls rework): defaults are now `false` and the toggle is single-click. **Follow-up (Track Q):** golden-image test comparing export with onion skin on/off — blocked on there being a test project.

Fixed by the transform-tool rewrite (`PixelTransformTool` / `SelectionController`): copy-on-write working-bitmap snapshots prevent tearing mid-transform (a638463), `MoveThumbNode` now raises a cancel event on interrupted drags (9dc8b41), and click-outside commits the transform instead of dropping it (4a5b18d) — a box-selection drag no longer disconnects partway through. **Follow-up (Track Q):** pointer-event regression test once a test project exists.
- [x] Pixel-perfect stroke flicker — [#241](https://github.com/gritsenko/Pix2d/issues/241). Resolved by the pixel-perfect drawing rework (swap-bitmap preview management `03b4282`, incremental preview + optimized bitmap handling `cf92167`, earlier `9e2e39f`); confirmed fixed in current builds.
- [x] Slider mouse-wheel support on desktop — [#242](https://github.com/gritsenko/Pix2d/issues/242) (small UX win, cheap). `SliderEx` adjusts on `PointerWheelChanged` while hovered (one notch = 1 step, Ctrl = 10, clamped to min/max); the event is marked handled so a parent `ScrollViewer` doesn't scroll instead.
- [x] **`SliderEx` redesigned to the Figma "filled value" control** ([`SliderEx.cs`](../Sources/Core/Pix2d.Core/UI/Shared/SliderEx.cs)). Replaced the old three-layout control (two-line / one-line / narrow-popup, each a stock `Slider` + `NumericUpDown`) with **one unified box** matching the redesign: a rounded track whose **accent orange→amber fill grows left→right as a background band** proportional to `(Value−Min)/(Max−Min)`, the uppercase label stacked over the current value inside the box, and the units on the right. Text stays in the light foreground tiers over the fill (the dark track is the *background*, never painted over the text — per design feedback). Interaction mirrors `Pix2dColorPicker`'s hue bar: **press + drag anywhere scrubs** (absolute mapping, pointer captured with `Handled` — carries over the #236 capture-steal hardening), the **mouse wheel** nudges (#242), and a **click without drag opens a keyboard text field** (autofocus + select-all, accent border) that commits on Enter / focus-loss and cancels on Esc or the ✕ button. Public API (`Label/Units/Minimum/Maximum/Value` + `ValueChanged`) unchanged, so all ~10 call sites keep working; the dead `LayoutMode`/`NarrowMode`/`NarrowWidthThreshold` props + enums were removed and the one consumer that set them ([`MagicWandToolSettingsView`](../Sources/Core/Pix2d.Core/Plugins/Drawing/UI/MagicWandToolSettingsView.cs)) now sets an explicit width. **Verified** end-to-end against a running Debug build via the AgentTools inspector (brush panel: fill band + light text on OPACITY, click→text-edit with ✕ on SIZE).
- [x] Palette slider interruption — [#236](https://github.com/gritsenko/Pix2d/issues/236). Not reproducible on desktop; hardened preventively: `Pix2dColorPicker` now marks its color-square / hue-slider pointer events `Handled` so a parent `ScrollViewer`'s touch `ScrollGestureRecognizer` can't hijack the pointer mid-drag and steal the capture (the capture-steal is what interrupted the drag on touch). Same class of fix as the slider mouse-wheel handling in [#242].
- [x] Grid toggle did nothing — enabling "Show grid" in the grid-settings flyout never showed the grid. `GridSettingsView.State` captured a single `ViewPortState` instance at construction; the flyout is built once with `MainView` (before the first real project is current, and stale after every tab switch), so toggles wrote to an orphaned `ViewPortState` that no watcher — `SnappingService`/`ViewPortRefreshService` both rebind via `WatchForCurrentProjectViewPort` — ever observed. Fixed by making the view resolve `AppState.CurrentProject.ViewPortState` **live** on every read/write and rebind through `WatchForCurrentProjectViewPort` (which also reflects the Ctrl+. `ToggleGrid` shortcut back into the switch) — the same stale-binding gotcha documented in `CLAUDE.md`. Verified end-to-end against a running Debug build via the AgentTools inspector (flyout switch toggle now drives the active project's grid node in both directions).
- [x] Narrow-screen (phone-portrait) dialogs/banners overflowed the viewport. On a ~290px window the telemetry-consent dialog (fixed `.Width(400)`), the unsaved-changes dialog (three fixed 100px buttons), and the crash-recovery banner (non-wrapping horizontal row) spilled off-screen. Fixed at two levels: (1) systemic — [`PopupView`](../Sources/Core/Pix2d.Core/UI/Shared/PopupView.cs) (the dialog host) now clamps its width to the viewport (`MaxWidth` + a restore-able `MinWidth` clamp) and re-fits on parent resize/rotation via a `Bounds` subscription bound in `ApplyPositionForCurrentLayout`; [`DialogContainer`](../Sources/Core/Pix2d.Core/UI/Shared/DialogContainer.cs) now starts `IsOpen(false)` so the *first* dialog shown (startup telemetry prompt) actually fires `OnOpened` and gets the clamp. (2) per-view — telemetry/unsaved dialogs use `MaxWidth` + stretched-column button rows (no fixed widths), text wraps; the recovery banner ([`MainView`](../Sources/Core/Pix2d.Core/UI/MainView.cs)) stretches with margins under a `MaxWidth(560)` cap with a wrapping text column. Also localized + wrapped the previously hardcoded unsaved-changes strings. Verified end-to-end via the AgentTools inspector (`set_window_size` 290→266px clamp, `layout_audit` clean, no overflow) for all three at phone-portrait width.
  - **Follow-up (done):** repositioned the crash-recovery banner from centre-screen to a top notification zone directly under the top toolbar (a Row-2 slot in the full-width top strip in [`MainView`](../Sources/Core/Pix2d.Core/UI/MainView.cs)); on a narrow screen its Dismiss button now wraps onto its own line. Re-enabled the previously commented-out **rate/review prompt** in the same zone and made it responsive — [`RatePromptView`](../Sources/Core/Pix2d.Core/UI/RatePromptView.cs) now uses the shared `notify-card`/`notify-content` styles (centred one-row on desktop, stretched + actions-stacked on narrow) and its `IReviewService` ctor arg defaults to null so it builds on desktop/web (where the prompt stays hidden) instead of throwing. Both banners share global `notify-card`/`notify-content` styles in [`AppStyles`](../Sources/Core/Pix2d.Core/UI/Styles/AppStyles.cs) (global so they also reach the nested `RatePromptView`). **Tool/action bars** ([`TopToolUiContainer`](../Sources/Core/Pix2d.Core/UI/TopToolUiContainer.cs), [`ActionsBarView`](../Sources/Core/Pix2d.Core/UI/ActionsBarView.cs)) — especially the wide selection-tool settings — now scroll horizontally instead of clipping off-screen: each is a horizontal `ScrollViewer` whose width is clamped to the window client size via [`ViewportSizeExtensions.ClampMaxWidthToViewport`](../Sources/Core/Pix2d.Core/UI/Shared/ViewportSizeExtensions.cs) (a plain `MaxWidth` or star column can't bound them here — the bottom side-panels contaminate the grid's Auto columns' width). Verified via AgentTools at 290/800/900px.
- [x] Ctrl+S on a PNG-backed project should overwrite the source image — [#200](https://github.com/gritsenko/Pix2d/issues/200) (Hot, `complexity:low`). When a project was opened from a flat `.png` and is still a single sprite / single layer / single frame, `ProjectService.SaveCurrentProjectAsync` now writes back to the original PNG (via the existing `IExportService.ExportNodesToFileAsync` render path) instead of popping a "Save as .pix2d" dialog. `ProjectState.File` already keeps the opened source reference, so no new tracking was needed; the extension match is case-insensitive. Adding a layer/frame/artboard changes the shape so it correctly falls through to the project save. Desktop-only (Android/WASM use `UseInternalFolder`). One-file change in [`ProjectService.cs`](../Sources/Core/Pix2d.Core/Services/Project/ProjectService.cs) (+ `IExportService` ctor dep). **Verified** (manual, desktop): editing a PNG-backed single-layer/frame project and pressing Ctrl+S overwrites the source image silently; adding a layer/frame falls back to the `.pix2d` Save As.
- [x] Palette doesn't highlight the picked color — [#220](https://github.com/gritsenko/Pix2d/issues/220) (Hot, `bug`, `complexity:low`). Root cause: the [`ColorPalette`](../Sources/Core/Pix2d.Core/UI/Shared/ColorPalette.cs) control had no concept of a "selected" swatch — every swatch drew the same fixed border, and nothing compared the current color to palette entries. Added a `SelectedColor` `DirectProperty` (the Markup.Declarative generator auto-emits the `.SelectedColor(...)` binding) that highlights the matching swatch (2px full-opacity white border) via an in-place restyle (no rebuild churn during HSV drag), and bound it to the existing `state.SelectedColor` — which already tracks the eyedropper pick through `SpriteEditorState.CurrentColor` — on both the Recent and Custom palettes in [`ColorPickerView.cs`](../Sources/Core/Pix2d.Core/UI/ColorPickerView.cs). **Verified end-to-end** via the AgentTools inspector: selecting a color highlighted the matching swatch in both palettes (2px white ring) while non-matching swatches kept the dim border.
- [x] Show the eyedropper cursor + toolbar highlight while Alt is held over a brush — [#184](https://github.com/gritsenko/Pix2d/issues/184) (`UX/UI`). Holding Alt over a brush-family tool (`PixelBrushToolBase`: Brush/Eraser/pixel Shape) makes it pick a color instead of draw, but there was no visible feedback until now. Added a transient `ToolsState.IsColorPickerModeActive` flag that [`SkiaCanvas`](../Sources/Core/Pix2d.Core/SkiaCanvas.cs) (owns key events + cursor) sets on Alt-down/clears on Alt-up (and on tool switch, so it can't stick), driving a picker cursor (`StandardCursorType.Cross`), and had [`ToolItemView`](../Sources/Core/Pix2d.Core/UI/ToolBar/ToolItemView.cs) OR the eyedropper's toolbar highlight on the same flag. Three small files, no new subsystem. *Note: Avalonia has no stock eyedropper cursor — `Cross` is the zero-asset approximation; a custom bitmap cursor from icon glyph `\xE91B` is a possible follow-up.* **Verified** (manual, desktop).
- [x] `ArgumentOutOfRangeException` in `LayersView.State.InvalidateThumbnailItems` — Sentry crash on 3.9.0 (Android, 19 events / 6 users). Root cause: the index-based overload did `Layers[ReverseIndex(index)]` where `ReverseIndex = Layers.Count - index - 1`. An operation's `AffectedLayerIndexes` are captured at operation time and can fall outside the UI's `Layers` mirror (operation targeting a different sprite/frame than the one displayed, a layer-count mismatch, or the mirror not yet reloaded on tab/artboard switch), producing a negative or too-large index that threw on the indexer — surfacing as an unobserved-task crash via `OnOperationInvoked`. Fixed by bounds-checking the reversed index in [`LayersView.cs`](../Sources/Core/Pix2d.Core/UI/Layers/LayersView.cs) and skipping out-of-range entries (matching the null-safe `FirstOrDefault` pattern of the sibling `Layer`-based overload); a skipped thumbnail refreshes on the next `ReloadLayers`, so it's cosmetically harmless.
- [x] `NotImplementedException` — Sentry crash on 3.9.0 (Android, "Arg_NotImplementedException", no frames). The most probable trigger: **Bake effect** (layer effects UI → `EffectsService.BakeEffect` → `BakeEffectOperation`) called [`EffectExtensions.ApplyToBitmap`](../Sources/Core/SkiaNodes/Extensions/EffectExtensions.cs), which unconditionally threw `NotImplementedException` — baking *any* layer effect crashed on every platform. Implemented it mirroring `SKNodeRenderer.RenderEffectsToSurface` (bitmap → surface, `effect.Render(rc, surface)`, pixels read back); verified for all three effect types (Replace/Back/Overlay: grayscale converts, shadow preserves content + offsets, outline renders). Also defused the other reachable NIE stubs: `AndroidPlatformStuffService.ToggleTopmostWindow`/`OpenAppDataFolder` and the browser `OpenAppDataFolder` are safe no-ops, and the `ClipboardCommands` General-context Copy/Paste/Cut placeholders log a trace instead of throwing. *(Correction, 2026-07-28: those placeholders are **not** actually bound to Ctrl+C/V/X — `ClipboardCommands` is registered nowhere, so they are unreachable dead code rather than live commands. Discovered while wiring the General action bar; see the General-context entry below.)* Remaining NIE stubs (`BitmapNode.Clear`/`ModifyBitmap`/…, `SelectionService.SelectNext`, `EditContext.Title`) are verified-unreachable dead code. See the Track Q diagnostics entry for why the Sentry event was frame-less and how that's fixed.
- [x] `InvalidOperationException: "Bitmap is null"` on **Undo** — appstat handled-error on 3.9.0 (Android, 11 events / 1 user, burst). Stack: `BitmapNode.GetData` → `Pix2dSprite.GetData` → `DrawingOperationWithDiffState.ApplyChanges` → `OnPerformUndo` → `OperationService.Undo`. The undo diff-apply reads `target.GetData()`; a frame's `SpriteNode` can reach that path with a null `Bitmap` (partial session restore, or the node's pixels disposed on unload while the operation history still references it). The hard throw aborted the undo *and* left the stack inconsistent (`Undo` pops the op but never pushes it to redo — line ~239/244 in [`OperationService.cs`](../Sources/Core/Pix2d.Core/Services/OperationService.cs)), so hammering undo spammed the error. Fixed in [`BitmapNode.cs`](../Sources/Core/Pix2d.Shared/CommonNodes/BitmapNode.cs): `GetData`/`SetData` now go through an `EnsureBitmap()` helper that lazily re-allocates a blank bitmap sized to the node's known `Size` (mirroring the existing lazy create in `OnSizeChanged`, `Pix2DAppSettings.ColorType`), so the diff re-applies and undo keeps working; it still throws only when `Size` is genuinely unknown (0×0 — nothing recoverable). The frame-less `NullReferenceException` on 3.9.0 (4 events / 2 users) whose first occurrence falls inside the *same* burst window is most likely a downstream cascade of this broken-undo state and should subside with this fix.
- [x] `ArgumentOutOfRangeException` in `TimeLineView.State.OnOperationInvoked` — appstat handled-error on 3.9.0 (Android, 8 events / 3 users). Exact sibling of the `LayersView` thumbnail crash above: on undo/redo of an `ISpriteEditorOperation`, `Frames[index]` used the op's `AffectedFrameIndexes` (captured at operation time) directly, which can exceed the active sprite's current `Frames.Count` (frames deleted, or a different artboard now drives the timeline). Fixed by bounds-checking the index and skipping out-of-range entries in [`TimeLineView.cs`](../Sources/Core/Pix2d.Core/UI/Animation/TimeLineView.cs) — a skipped frame thumbnail refreshes on the next `ReloadFrames`.
- [x] `IndexOutOfRangeException` in `DrawingOperationWithDiffState.ApplyChanges` on **Undo** — appstat handled-error on 3.9.0 (Android/Windows, 22 events / 2 users). Stack: `ApplyChanges` → `OnPerformUndo` → `OperationService.Undo` → `EditCommands.Undo`. Sibling of the "Bitmap is null on Undo" fix above (same method) but a *size-mismatch* failure mode: the undo replays a run-length diff whose block lengths sum to the target's pixel count captured when the operation ran, writing them sequentially into `target.GetData()`. If the drawing target was resized since (crop/resize replayed out of order, or a different-sized artboard is now the target), the runs overrun the current buffer → out-of-range write. Fixed in [`DrawingOperationWithDiffState.cs`](../Sources/Core/Pix2d.Shared/Operations/Drawing/DrawingOperationWithDiffState.cs): `ApplyChanges` now compares the total diff length against the current pixel buffer and skips the apply (logged via `Logger.Trace`) when they differ — avoiding both the crash and the memory corruption a partial write would cause on a mismatched buffer.
- [x] Autosave temp-file races — appstat handled-errors on 3.9.0/3.10.0 (Android, 5 signatures: `FileNotFoundException`/"Could not find file"/"used by another process" on `Sessions/active/<id>/frames/<key>.png.tmp`). Root cause: `AutoSaveService.ForceSaveSync` (Android `OnPause` / window close) runs the commit on a background task with a bounded wait; on **timeout it releases `_commitLock` while that commit keeps running**, so a later periodic `TickOnceAsync` can start a *second* `CommitAsync` on the same store, colliding on the deterministic `<key>.png.tmp` path — the create fails ("used by another process", `FileShare.None`), or the sibling's `File.Move` already consumed the temp → FileNotFound. Fixed by adding a per-store commit gate (`SemaphoreSlim`) in [`IncrementalSessionStore.CommitAsync`](../Sources/Core/Pix2d.Core/Services/AutoSave/IncrementalSessionStore.cs) so an overlapping commit waits instead of racing, restoring the one-commit-per-store invariant at the store level (where it matters) rather than only at the service lock.
- [ ] `InvalidOperationException: "Peer instance does not implement T."` — appstat handled-error on 3.9.0 (Android, 4 events / 2 users, single burst incl. an emulator). Frame-less; thrown inside Avalonia's automation-peer subsystem (triggered by Android accessibility/TalkBack enumerating peers), not app code — no custom `AutomationPeer` exists in the repo. Not app-fixable at the current stack detail; revisit if it recurs with a usable frame or on an Avalonia upgrade.
- [ ] **3.10.0 store rollout — three frame-less appstat signatures (desktop/Windows, `SentryLevel.Fatal`).** First seen on the 3.10.0 build that shipped consent-gated telemetry, so they were **surfaced, not introduced**, by the new `CaptureHandled`/`CaptureFatal` path — each carried only its exception header (type + message), no frames. Signatures: (1) `ArgumentException: "UnsupportedType (Parameter 'Decimal')"` (6 events / 1 user, 2-min burst) — string isn't anywhere in the source, so it's a library resource thrown in a real path (serialization/conversion of a `Decimal`); ruled out the new analytics client (`AppStatTrackingClient.WriteValue` handles `decimal`, and analytics metrics are `double`). (2) `Exception: "Unable to allocate pixels for the bitmap."` — SkiaSharp OOM allocating an `SKBitmap` (large canvas resize/export/import). (3) `UnauthorizedAccessException: "Access to the path 'C:\Windows\System32\…png' is denied."` — **root-caused and fixed, see the next item**. (1) and (2) remain **blocked on a usable stack**; the Track Q *reported-exception stack guarantee* below makes the next occurrence locatable. Likely follow-ups once framed: treat expected IO (`UnauthorizedAccessException`/`IOException`) on export/save and `SKBitmap` allocation OOM as **handled, user-facing** errors (toast/dialog) instead of fatals that reach the global handlers.
- [x] **Save/export dialogs defaulted to `C:\Windows\System32`** — `UnauthorizedAccessException` recurring across 3.10.0 → 3.11.1 (Windows, 4 signatures, one per user-typed file name: `bd.png`, `bobbin.gif`, `Shiney.png`, `Coucher de soleil.png`). Root cause: `AvaloniaFileService` never set `SuggestedStartLocation` on any picker, so the Win32 dialog opened on the **process working directory** — which is `C:\Windows\System32` when Pix2d is launched through its file association (`shell\open\command` passes no working directory). Users accepted that folder and the write failed. The `contextKey` parameter threaded through every `IFileService` overload for exactly this purpose was accepted and **silently ignored**, and its reserved settings key `SettingsConstants.FileServiceContexts` was unused. Fixed in [`AvaloniaFileService`](../Sources/Core/Pix2d.Core/Services/AvaloniaFileService.cs): open/save/folder pickers now start in the last folder used for that context (persisted as a `contextKey → path` map under `FileServiceContexts`), falling back to **Documents** — so the default is always writable and the documented per-context folder memory finally works. Two latent bugs in the same area fixed alongside: [`AvaloniaFolder.GetFileName`](../Sources/Core/Pix2d.Core/Common/FileSystem/AvaloniaFolder.cs) called `Path.Combine` with a *single* argument, dropping the folder and handing a bare relative name to `File.OpenWrite` (another CWD write, plus a de-dup `File.Exists` check that probed the wrong directory and so silently overwrote existing exports); and `AvaloniaFolder.Path` used `Uri.AbsolutePath`, which yields `/C:/a/My%20Art` — not a usable filesystem path. Split into `GetFilePath` (full path, for raw `File`/`Directory` APIs) and `GetUniqueFileName` (name only, for `IStorageFolder.CreateFileAsync`). Shipped in **v3.11.2**; all four `System32` signatures resolved in appstat on 2026-07-27. The sibling signature on a user's *own* file (`…\Documents\Spider_SpriteSheet.png`) is **not** covered by this and stays open — that write was genuinely denied (read-only / locked / sync-held file), which is the "treat expected IO as a handled, user-facing error" follow-up noted above, not a bad default folder.
- [x] **3.11.1 crash hardening.** Two independent fixes shipped together: (1) [`ExportView`](../Sources/Core/Pix2d.Core/UI/Export/ExportView.cs) now catches exceptions from `RenderToBitmap` when generating an export preview, so an oversized preview render (OOM on a very large canvas) shows a graceful state instead of crashing the app. (2) [`MainActivity.DispatchKeyEvent`](../Sources/Heads/Pix2d.Droid/MainActivity.cs) (Android) now swallows an `IndexOutOfRangeException` coming from an Avalonia.Android bug in its own key-dispatch internals — not app code, but it was reaching the app as an unhandled crash.
- [x] **Timeline frame-reorder / delete `ArgumentOutOfRangeException`** — two new appstat signatures on 3.11.1 (Android): `"Index must be within the bounds of the List"` (fatal, on `List<LayerFrameMeta>.Insert` in [`ReorderAnimationFramesOperation`](../Sources/Core/Pix2d.Core/Plugins/Sprite/Operations/Animation/ReorderAnimationFramesOperation.cs)) and `"Index was out of range"` (on `Layer.GetFrameByIndex` in [`DeleteAnimationFrameOperation`](../Sources/Core/Pix2d.Core/Plugins/Sprite/Operations/Animation/DeleteAnimationFrameOperation.cs)). Root cause: the timeline `Frames` collection carries an extra `IsAddFrame` placeholder at index == frameCount, and [`ItemsListContextDragBehavior`](../Sources/Core/Pix2d.Core/Common/Behaviors/ItemsListContextDragBehavior.cs) treated it as an ordinary draggable item — dragging it, or dropping a real frame onto its slot, produced a `newIndex`/`oldIndex` one past the real-frame range. Worse, the reorder mutated layers one at a time, so a throw mid-loop left layers with **mismatched frame counts**, which then blew up a later per-layer delete (the second signature). Fixed at two levels: (1) [`TimeLineView.OnFramesReordered`](../Sources/Core/Pix2d.Core/UI/Animation/TimeLineView.cs) rejects the placeholder as a drag source and clamps a drop-on-placeholder to the last real frame (rebuilding the VM order the `Move` mangled); (2) both operations now validate the indices against **every** layer before mutating any of them, so a bad index is a clean no-op instead of a partial, project-corrupting mutation. The reorder signature (`List.Insert`) is fully covered by this; the `GetFrameByIndex` one had a **second, independent root cause** — see the next item. Both fixes shipped in **v3.11.2** (verified present in the tagged tree) and both signatures were resolved in appstat on 2026-07-27. Note the earlier lesson: they were resolved on 2026-07-23 while still unreleased and auto-reopened — expect the same if the Android staged rollout leaves enough 3.11.1 users to keep reporting, which is exactly the signal auto-reopen exists for.
- [x] **Stale frame index kills the next brush stroke** — `"Index was out of range"` on 3.11.1 (Android, 12 events / 6 users in 7 days; the single largest live signature). Stack: pointer-down → `DrawingLayerNode.BeginDrawing` → `DrawingService.StartNewDrawingOperation` → `Pix2dSprite.GetData` → `Layer.GetSpriteByFrame` → `Layer.GetFrameByIndex` → `List<LayerFrameMeta>[index]`. Distinct from the reorder fix above: the *sprite's* frame pointer itself goes out of range. `Pix2dSprite.SetFrameIndex` wrote `_currentFrameIndex` **unvalidated**, and only `Layer.SetFrame` clamped — to the layer's private copy, while every drawing path reads the sprite-level `CurrentFrameIndex` and forwards it straight to `Frames[..]`. `Layer.SetFrame` also early-returned on an unchanged value *before* clamping, so a repeated index survived frames being deleted under it; and layers that desync in frame count make an index valid for one layer out of range for another. Root cause is two independent bugs in how it drove the v1 submission API, both confirmed against the docs: (1) `Update-ApplicationSubmission` leaves a cloned submission's packages untouched unless `-AddPackages`/`-ReplacePackages` is passed, so setting `ApplicationPackages = @()` in the JSON was a no-op; (2) the SAS `fileUploadUrl` expects a **ZIP whose entries match `applicationPackages[].fileName` with `fileStatus=PendingUpload`**, not a bare `.msixupload` (`Set-SubmissionPackage` only PUTs the file you hand it). *The API itself never changed* — MSIX still submits through `manage.devcenter.microsoft.com/v1.0/my/applications/…`, with no deprecation notice; what changed is the tooling Microsoft documents ([msstore CLI](https://learn.microsoft.com/windows/apps/publish/msstore-dev-cli/github-actions), actively developed, vs StoreBroker which is legacy and no longer referenced from the docs). The v2 API (`/submission/v1/product/…`) is **MSI/EXE only** and explicitly not for MSIX, so there is nothing to migrate to. **Shipped** (final shape — the two intermediate designs and why they were wrong are recorded below): `microsoft/microsoft-store-apppublisher@v1.1` → `msstore reconfigure` → `msstore publish <bundle> -id 9NBLGGH1ZDFV` as a single command. The CLI performs the whole clone → declare packages → zip → upload → commit dance itself, and since [Dec 2025](https://github.com/microsoft/msstore-cli/commit/311d3d20) also marks superseded packages `PendingDelete` (which is what the old job's empty-array hack was reaching for). Constraints encoded in the workflow comments: needs a new `SELLER_ID` secret (StoreBroker didn't use one) and the Manager role on the Entra app; msstore [hard-refuses non-free products](https://github.com/microsoft/msstore-cli/issues/115) (`pricing.priceId == "Base"` → aborts *and deletes the draft*) — Pix2d is free (DisplayCatalog reports `listPrice 0.0`), so it passes; and an API-created submission must never be touched by hand in Partner Center or it can no longer be committed via the API. **Dry run passed (2026-07-27, submission `1152921505701500952`, `version=3.11.3`):** submission created → `Pix2d_3.11.3.0_x64_arm64.msixbundle` zipped, PUT accepted (200) and uploaded to `ingestionpackagesprod1` → left at `PendingCommit`. The Partner Center UI showed *Packages: Unchanged*, which looks exactly like the StoreBroker failure but isn't — a `PendingUpload` entry has no version/architecture until the commit ingests the ZIP, so the UI keeps rendering the last published set. Proven by reading the submission back with a throwaway read-only probe workflow (`store-submission-inspect.yml`, added in `fb3f231` and deleted once the pipeline was proven — restorable from history; it just ran `msstore submission status/get` and printed the arrays): `Pix2d_3.11.3.0_x64_arm64.msixbundle → PendingUpload` alongside `Pix2d_3.11.2.0_x64_arm64.msixbundle → PendingDelete`. Two things that probe also surfaced: the Store tracks the *bundle's* date-derived `Identity/@Version` (`2026.725.1408.0`) rather than `Pix2dVersion`, and the legacy `.msixupload` packages (3.11.1.0 and older) stay `Uploaded` forever because msstore only supersedes the package sharing the new file's extension. **Commit verified (2026-07-27, submission `1152921505701501667`):** the commit ingested the ZIP and Partner Center listed `Pix2d_3.11.3.0_x64_arm64.msixbundle` as **Validated** — so the API path accepts an **unsigned** bundle exactly like the web upload does, which was the last open question. That run still ended `CommitFailed` with a single `InvalidState` error ("The requested action conflicts with an existing resource. Please refresh the page and try again"), which msstore surfaces as the far more alarming *"active validation errors which cannot be exposed via API"*. It was a concurrency conflict, not a validation problem: the dashboard page for that submission was open in a browser during the commit, and clicking **Submit for certification** on the very same submission afterwards went through cleanly. So: keep the submission closed in Partner Center while the job runs; recovery from a failed commit is just a re-run, since msstore deletes a failed pending submission and creates a fresh one. **That run also exposed a defect in the job itself** — it was structured as `msstore publish -nc` followed by `msstore submission publish`, and the latter returns 0 the moment the commit is *accepted*, so the workflow went green while the submission failed minutes later. Now it is a single `msstore publish` without `-nc`, which polls until the submission leaves `CommitStarted`, prints the `statusDetails` tables and exits non-zero on `CommitFailed`. **End-to-end green on the re-run with the dashboard closed** (run `30296671956`): `Submission Status - PreProcessing` → `Submission commit success!`, and the printed package list shows `Pix2d_3.11.3.0_x64_arm64.msixbundle` with `Pix2d_3.11.2.0_x64_arm64.msixbundle` gone — the supersede-and-replace the StoreBroker job never managed. 3.11.3 went to certification as a **Store-only** build (no `v3.11.3` tag, so the other channels stay on 3.11.2 — the daily `attach-store-msix` is unaffected because `v3.11.2` already carries its store-signed asset; a future full release must not reuse the 3.11.3 number with different content). **Now folded into the release pipeline:** the standalone `windows-store-msix.yml` is gone and its packaging + submission live in `release-publish.yml` as `build_store_msix`, which follows the same rule as `build_android` — a `v*` tag builds *and* submits (the Store equivalent of the automatic Google Play production push), a manual dispatch builds only unless `submit_to_store` is ticked. The Store therefore stops being a separate manual chore in the release checklist.

- [ ] **Cross-platform "rate the app" prompt** `P2` — the prompt heuristics/UI ([`ReviewService`](../Sources/Core/Pix2d.Core/Services/ReviewService.cs) + [`RatePromptView`](../Sources/Core/Pix2d.Core/UI/RatePromptView.cs)) were already cross-platform; only a concrete `IReviewService` was Android-only, so desktop/web never showed it. **Shipped:** `DesktopReviewService` routes by distribution channel — MS Store (MSIX) build → native `StoreContext.RequestRateAndReviewAppAsync` dialog (fallback `ms-windows-store://review/?ProductId=9NBLGGH1ZDFV`); portable / itch.io / Gumroad / Linux / macOS → the `pix2d.com/review` hub (the binary can't know its download channel, so the site — updatable without a release — picks the destination). `IPlatformStuffService.IsStorePackage` gates it; the service is force-constructed at startup so Save/Export triggers are live. **Conversion funnel** logged to appstat (`stats.pix2d.com`) as `*Review:` custom events — `Showing prompt` (banner impression) → `Accepted`/`Dismissed` (banner response) → channel detail (`Store dialog` with `result=Succeeded/CanceledByUser/…`, `Opened store page`, `Opened review hub`, `In-app review requested`); all events share one funnel's context/promptsCount/workTime props via `ReviewService.LogReview`. **Remaining:** (1) build the `pix2d.com/review` hub page that reads `?src/os/pkg/v` and offers MS Store / itch / Gumroad / GitHub-star / Telegram CTAs; (2) `WebReviewService` on the WASM head → same hub (`?src=web`); (3) localize the hard-coded English prompt strings in `ReviewService`; (4) if Pix2d ever ships on the Mac App Store, add a `macappstore://…?action=write-review` branch.
  - **Follow-up (3.11.1, done):** the 2-hour work-time gate in `TrySuggestRate` could never pass — `TotalWorkTime` was only persisted from `SaveTotalWorkTime()`, whose sole caller `Dispose()` is never reached in the real app lifecycle (Android backgrounds/kills via `OnPause`/`OnStop`/`OnDestroy`; desktop's `OnAppClosing` doesn't touch this service either), so the stored value stayed `0` forever. Fixed in [`ReviewService.cs`](../Sources/Core/Pix2d.Core/Services/ReviewService.cs): a new `GetTotalWorkTime()` computes the total live (persisted total + elapsed since `LaunchTime`) instead of relying on a flush point that never fires, and the previous session's elapsed time is folded in at the start of the next one.
  - **Follow-up (post-3.11.1, done) — the whole prompt gate was a no-op, and the settings layer hid it.** Production funnel data from the 3.11.1 Android rollout showed the prompt firing **on a fresh install 1m26s into the first session**, `Accepted` logged **twice** a second apart, the banner **re-shown after the user had already rated**, `promptsCount` stuck at `0`, and the nonsense `workTime=739820+days`. One root cause explains all five: [`ISettingsService`](../Sources/Core/Pix2d.Shared/Abstract/Services/ISettingsService.cs) resolves keys to properties **on `AppSettings` by name** via reflection, and **none of the review-funnel keys were ever declared there** — so every `Set` silently no-op'd and every `Get` returned `default`. `LaunchTime` read back as `default(DateTime)`, making `DateTime.Now - launchTime` ≈ 739820 days, which sails through the 2-hour gate; `IsAppReviewed`/`NextPromptTime`/`AppReviewPromptsCount` never persisted, so nothing could ever terminate or defer the funnel. Fixes: (1) declared all funnel keys in [`AppSettings.cs`](../Sources/Core/Pix2d.Core/Services/AppSettings.cs) (`LaunchTime`, `TotalWorkTimeTicks`, `IsAppReviewed`, `NextPromptTime`, `AppReviewPromptsCount`, `IsInAppReviewShown`) — the cumulative total is stored as `long` ticks rather than a `TimeSpan` so it round-trips through System.Text.Json unambiguously, and all call sites now use `nameof(AppSettings.X)` instead of loose string literals; (2) `GetSessionTime()` treats a missing/`default` `LaunchTime` as *zero* elapsed, so an unwritable settings file leaves the gate **closed** rather than wide open; (3) `RateApp()` is re-entrancy-guarded and owns the `IsAppReviewed` write (it awaits a platform dialog for seconds, and [`WindowCommands`](../Sources/Core/Pix2d.Shared/Commands/WindowCommands.cs) now dismisses the banner *before* awaiting — the live button is what produced the double `Accepted`); (4) `TrySuggestRate` bails when the banner is already on screen, logs the impression *after* the counter increment (so `promptsCount` identifies *this* impression instead of always trailing by one), and applies a 3-day cooldown to an impression the user simply ignores, which previously left no state and re-prompted on the very next save.
  - **Follow-up (post-3.11.1, done) — same bug class, two more dead settings.** Auditing every `ISettingsService` key against `AppSettings` found two more that silently never persisted: **`IsAutoOpenTransformEditorAfterSelectionEnabled`** (the Settings toggle reverted to `true` on every launch) and **`lastUpdateCheckUtc`** (the update-check throttle in [`UpdateService`](../Sources/Core/Pix2d.Core/Services/UpdateService.cs) never held, so it re-checked every launch); both now have properties. To stop this class of bug recurring silently, [`SettingsService.Set`](../Sources/Core/Pix2d.Core/Services/SettingsService.cs) now **logs once per unbacked key** instead of discarding the write without a trace — a silent write loss cost a full release. *Note: the legacy `CrashTelemetryConsent` migration read in `CrashReportService` is dead for the same reason (the key never had a property, so no user ever had it persisted); harmless now that 3.11 is well past that migration, and left unbacked deliberately so it doesn't add a dead field to `pix2d_settings.json`.*

## 10. Non-goals (explicitly out of scope)

- General-purpose raster editor (competing with Krita/Photoshop) — stay pixel/sprite-focused.
- Building/hosting our own image-generation models — integrate providers, never own inference.
- A binary plugin marketplace with payments/DRM — curated list only.
- Vector tools beyond pixel-perfect shape primitives.
